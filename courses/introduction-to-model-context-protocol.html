آشنایی با پروتکل MCP؛ ساختن سرور و کلاینت از صفرIntroduction to Model Context Protocol

10 lessons · 1 quiz · 1 hr · badge صفحهٔ رسمی در Claude Academy ↗

مناسب برای مهندس‌هایی که پایتون پایه، async/await و کار با API را بلدند. Engineers with basic Python, async/await and API familiarity.

۰ از ۱۰ خوانده شده

The Model Context Protocol (MCP) is an open standard that lets an AI application plug into tools and data in a uniform way. Instead of writing custom integration code for every service, a service publishes an MCP server, and any MCP client (Claude apps, Claude Code, your own app) can use it.

In this course you build both sides with the official Python SDK, through one hands-on project: a small document manager where Claude can read and edit documents, where your app can list and fetch them, and where users can run ready-made prompts like "reformat this doc in Markdown". Along the way you meet MCP's three building blocks: tools, resources and prompts.

پروتکل MCP (Model Context Protocol) یک استاندارد باز است که به یک اپ هوش مصنوعی اجازه می‌دهد به شکلی یکسان به ابزارها و داده‌ها وصل شود. به‌جای نوشتن کد اتصال اختصاصی برای هر سرویس، هر سرویس یک سرور MCP منتشر می‌کند و هر کلاینت MCP (اپ‌های Claude، Claude Code، اپ خودت) می‌تواند از آن استفاده کند.

در این دوره هر دو طرف را با SDK رسمی پایتون می‌سازی، آن هم در قالب یک پروژهٔ عملی: یک مدیر اسناد کوچک که در آن Claude می‌تواند سندها را بخواند و ویرایش کند، اپ تو می‌تواند فهرستشان را بگیرد و محتوایشان را بیاورد و کاربرها می‌توانند پرامپت‌های آماده‌ای مثل «این سند را به Markdown بازنویسی کن» را اجرا کنند. در این مسیر با سه آجر اصلی MCP آشنا می‌شوی: ابزارها، منابع و پرامپت‌ها.

درس ۱ · Lesson 1

معرفی MCPIntroducing MCP

صفحهٔ رسمی ↗

Imagine you're building a chat app that should work with GitHub. Without MCP, you write and maintain a tool for every GitHub action (list repos, read issues, open PRs…): schemas, functions, error handling, updates when GitHub changes. Multiply that by Slack, Jira, Google Drive…

MCP moves that work into an MCP server, usually written and maintained by the people who know the service best. Your app only needs an MCP client to connect. MCP is a communication layer that gives Claude context and tools without a lot of integration code on your side.

A server can offer three kinds of things:

  • Tools: actions the model can call (search issues, create a ticket).
  • Resources: data your app can read (a list of documents, a file's contents).
  • Prompts: ready-made, high-quality prompt templates users can run.

Common confusion: MCP is not a replacement for tool use. MCP servers *provide* tool definitions; Claude still uses them through normal tool calling. MCP just changes who writes and hosts the tools.

فرض کن داری یک اپ گفت‌وگو می‌سازی که باید با گیت‌هاب کار کند. بدون MCP، خودت باید برای هر کار گیت‌هاب (فهرست مخزن‌ها، خواندن issueها، باز کردن PR و…) یک ابزار بنویسی و نگهداری کنی: طرح‌واره، تابع، مدیریت خطا و به‌روزرسانی هر بار که گیت‌هاب چیزی را عوض کرد. حالا این را در اسلک، جیرا، گوگل درایو و… ضرب کن.

MCP این کار را به یک سرور MCP منتقل می‌کند که معمولاً همان کسانی که سرویس را بهتر از همه می‌شناسند می‌نویسند و نگهداری می‌کنند. اپ تو فقط یک کلاینت MCP لازم دارد تا وصل شود. MCP یک لایهٔ ارتباطی است که بدون کد اتصال زیاد در سمت تو، به Claude زمینه و ابزار می‌دهد.

یک سرور می‌تواند سه نوع چیز ارائه کند:

  • ابزارها (Tools): کارهایی که مدل می‌تواند صدا بزند (جست‌وجوی issue، ساختن تیکت).
  • منابع (Resources): داده‌ای که اپ تو می‌تواند بخواند (فهرست سندها، محتوای یک فایل).
  • پرامپت‌ها (Prompts): قالب‌های آماده و باکیفیت پرامپت که کاربرها می‌توانند اجرا کنند.

یک سوءتفاهم رایج: MCP جایگزین tool use نیست. سرورهای MCP تعریف ابزارها را *فراهم می‌کنند*؛ Claude هنوز از طریق همان فراخوانی ابزار معمولی از آن‌ها استفاده می‌کند. MCP فقط عوض می‌کند چه کسی ابزارها را می‌نویسد و میزبانی می‌کند.

Think of it like thisمثل این است که…

Before USB, every device had its own special plug. MCP is the USB of AI tools: one standard socket, so any app (the laptop) can use any service (the keyboard, the printer) without a custom cable for each.

قبل از USB هر دستگاه دوشاخهٔ مخصوص خودش را داشت. MCP مثل USB ابزارهای هوش مصنوعی است: یک سوکت استاندارد، تا هر اپ (لپ‌تاپ) بتواند از هر سرویس (کیبورد، پرینتر) استفاده کند بدون کابل اختصاصی برای هر کدام.

Pro tipنکتهٔ طلایی

Before writing your own integration, search for an existing MCP server for that service. Many companies publish official ones, and using them saves you maintenance forever.

قبل از نوشتن اتصال اختصاصی، دنبال یک سرور MCP موجود برای آن سرویس بگرد. خیلی از شرکت‌ها نسخهٔ رسمی منتشر کرده‌اند و استفاده از آن، تو را برای همیشه از نگهداری معاف می‌کند.

برنامه‌ای که ابزار، منبع یا پرامپت را با استاندارد MCP در اختیار کلاینت‌ها می‌گذارد.

درس ۲ · Lesson 2

کلاینت‌های MCPMCP clients

صفحهٔ رسمی ↗

The client is the bridge between your application and an MCP server. It sends requests and receives results using MCP's message types, for example:

  • ListToolsRequest → ListToolsResult ("what tools do you have?")
  • CallToolRequest → CallToolResult ("run this tool with these arguments")

MCP is transport-agnostic: the same messages can travel over standard input/output (a server running as a local process) or over HTTP (a remote server).

A full round trip in a chat app looks like this:

  1. User asks: "What repos do I have?"
  2. Your app asks the MCP client for the server's tool list and sends it to Claude with the question.
  3. Claude replies with a tool_use request.
  4. Your app asks the MCP client to call that tool; the server talks to GitHub and returns the result.
  5. Your app sends the result to Claude, which writes the final answer.

کلاینت پل بین اپ تو و یک سرور MCP است. با نوع‌های پیام MCP درخواست می‌فرستد و نتیجه می‌گیرد؛ مثلاً:

  • ListToolsRequest ← ListToolsResult («چه ابزارهایی داری؟»)
  • CallToolRequest ← CallToolResult («این ابزار را با این ورودی‌ها اجرا کن»)

MCP مستقل از روش انتقال است: همان پیام‌ها می‌توانند از طریق ورودی/خروجی استاندارد (سروری که به شکل یک پردازهٔ محلی اجرا می‌شود) یا از طریق HTTP (یک سرور راه‌دور) جابه‌جا شوند.

یک رفت‌وبرگشت کامل در یک اپ گفت‌وگو این‌طوری است:

  1. کاربر می‌پرسد: «چه مخزن‌هایی دارم؟»
  2. اپ تو از کلاینت MCP فهرست ابزارهای سرور را می‌گیرد و همراه سؤال برای Claude می‌فرستد.
  3. Claude با یک درخواست tool_use جواب می‌دهد.
  4. اپ تو از کلاینت MCP می‌خواهد آن ابزار را صدا بزند؛ سرور با گیت‌هاب حرف می‌زند و نتیجه را برمی‌گرداند.
  5. اپ تو نتیجه را برای Claude می‌فرستد و Claude جواب نهایی را می‌نویسد.

Think of it like thisمثل این است که…

The client is a translator at a business meeting. Your app speaks "app", the server speaks "service", and the translator makes sure every question and answer passes correctly in the standard language both understand.

کلاینت مثل مترجم یک جلسهٔ کاری است. اپ تو «زبان اپ» حرف می‌زند، سرور «زبان سرویس» و مترجم مطمئن می‌شود هر سؤال و جواب به زبان استانداردی که هر دو می‌فهمند درست منتقل شود.

Pro tipنکتهٔ طلایی

Notice who talks to Claude: your app, not the MCP server. The server never sees your conversation; it only receives specific tool calls. That's a useful boundary for privacy and security.

دقت کن چه کسی با Claude حرف می‌زند: اپ تو، نه سرور MCP. سرور هیچ‌وقت گفت‌وگوی تو را نمی‌بیند؛ فقط فراخوانی‌های مشخص ابزار را دریافت می‌کند. این مرز برای حریم خصوصی و امنیت مفید است.

Key wordsواژه‌های کلیدی

Transportروش انتقال
مسیری که پیام‌های MCP از آن جابه‌جا می‌شوند؛ مثل stdio یا HTTP.

درس ۳ · Lesson 3

تعریف ابزار با MCPDefining tools with MCP

صفحهٔ رسمی ↗

Writing JSON schemas by hand is tedious. The Python SDK's FastMCP lets you define a tool with a decorator on a normal Python function: the function name, its type hints and Field descriptions become the schema automatically.

In the course project, the server keeps a small set of documents in memory and offers two tools: one to read a document and one to edit it by replacing text. Clear names, descriptions and error messages matter, because Claude reads them to decide what to call.

نوشتن دستی طرح‌واره‌های JSON خسته‌کننده است. FastMCP در SDK پایتون اجازه می‌دهد یک ابزار را با یک دکوریتور روی یک تابع معمولی پایتون تعریف کنی: اسم تابع، نوع‌های ورودی و توضیح‌های Field خودبه‌خود به طرح‌واره تبدیل می‌شوند.

در پروژهٔ دوره، سرور چند سند را در حافظه نگه می‌دارد و دو ابزار ارائه می‌کند: یکی برای خواندن سند و یکی برای ویرایش آن با جایگزین کردن متن. اسم‌ها، توضیح‌ها و پیام‌های خطای روشن مهم‌اند، چون Claude آن‌ها را می‌خواند تا تصمیم بگیرد چه چیزی را صدا بزند.

Think of it like thisمثل این است که…

The decorator is a label maker. You write a normal function, stick a label on it ("read a document"), and the SDK turns the label into the official form Claude needs to understand the tool.

دکوریتور مثل یک دستگاه برچسب‌زن است. یک تابع معمولی می‌نویسی، رویش برچسب می‌زنی («یک سند را بخوان») و SDK آن برچسب را به فرم رسمی‌ای تبدیل می‌کند که Claude برای فهمیدن ابزار لازم دارد.

Pro tipنکتهٔ طلایی

Make error messages helpful to the model: include what went wrong and what would work ("Known ids: menu.md, lease.pdf"). Claude can then correct itself on the next try instead of guessing.

پیام‌های خطا را برای مدل مفید بنویس: بگو چه چیزی اشتباه شد و چه چیزی جواب می‌دهد («شناسه‌های موجود: menu.md، lease.pdf»). آن‌وقت Claude می‌تواند در تلاش بعدی خودش را اصلاح کند به‌جای حدس زدن.

Key wordsواژه‌های کلیدی

FastMCPFastMCP
بخشی از SDK پایتون MCP که ساختن سرور را با دکوریتورها ساده می‌کند.
Decoratorدکوریتور
نشانه‌ای مثل @mcp.tool بالای تابع که رفتار یا نقش آن را مشخص می‌کند.

درس ۴ · Lesson 4

بازرس سرور (Inspector)The server inspector

صفحهٔ رسمی ↗

You don't need a full chat app to test a server. The SDK includes a browser-based MCP Inspector: run your server in development mode, open the inspector in your browser, connect, and you can list the tools, fill in arguments, call them and see the exact responses and errors.

It's the fastest feedback loop for server work: change code, reconnect, call the tool again.

برای امتحان کردن یک سرور به یک اپ گفت‌وگوی کامل نیاز نداری. SDK یک بازرس MCP (MCP Inspector) مرورگری دارد: سرورت را در حالت توسعه اجرا کن، بازرس را در مرورگر باز کن، وصل شو و می‌توانی ابزارها را فهرست کنی، ورودی‌ها را پر کنی، صدایشان بزنی و جواب‌ها و خطاهای دقیق را ببینی.

سریع‌ترین چرخهٔ بازخورد برای کار روی سرور است: کد را عوض کن، دوباره وصل شو، ابزار را دوباره صدا بزن.

Think of it like thisمثل این است که…

The inspector is a test bench in an electronics workshop: you check the circuit with probes and a screen before you install it inside the finished product.

بازرس مثل میز تست در یک کارگاه الکترونیک است: قبل از نصب مدار داخل محصول نهایی، با پراب و صفحه‌نمایش چکش می‌کنی.

Pro tipنکتهٔ طلایی

Test the unhappy paths in the inspector too: a wrong document id, an empty string, a very long text. If the errors are clear to you, they'll be clear to Claude.

مسیرهای ناخوشایند را هم در بازرس امتحان کن: شناسهٔ اشتباه، رشتهٔ خالی، یک متن خیلی طولانی. اگر خطاها برای تو روشن‌اند، برای Claude هم روشن خواهند بود.

درس ۵ · Lesson 5

پیاده‌سازی یک کلاینتImplementing a client

صفحهٔ رسمی ↗

Now the other side. A client starts (or connects to) the server, opens a session, initializes it, and then can list and call tools. In the course, this logic is wrapped in a small MCPClient class so the rest of the app (the chat loop that talks to Claude) just asks "give me the tools" and "call this tool".

Most apps don't talk to the session directly everywhere; they keep one tidy wrapper and reuse it.

حالا طرف دیگر. یک کلاینت سرور را اجرا می‌کند (یا به آن وصل می‌شود)، یک جلسه (session) باز می‌کند، مقداردهی اولیه می‌کند و بعد می‌تواند ابزارها را فهرست کند و صدا بزند. در دوره این منطق داخل یک کلاس کوچک MCPClient پیچیده شده تا بقیهٔ اپ (چرخهٔ گفت‌وگو که با Claude حرف می‌زند) فقط بگوید «ابزارها را بده» و «این ابزار را صدا بزن».

بیشتر اپ‌ها همه‌جا مستقیم با session حرف نمی‌زنند؛ یک لایهٔ مرتب نگه می‌دارند و همان را دوباره استفاده می‌کنند.

Think of it like thisمثل این است که…

The client is like dialing a phone call: connect (start the server), say hello (initialize), ask "what can you do?" (list tools), then make requests (call tools), and hang up properly at the end.

کلاینت مثل گرفتن یک تماس تلفنی است: وصل می‌شوی (اجرای سرور)، سلام می‌کنی (مقداردهی اولیه)، می‌پرسی «چه کارهایی بلدی؟» (فهرست ابزارها)، بعد درخواست می‌دهی (فراخوانی ابزار) و آخرش درست قطع می‌کنی.

Pro tipنکتهٔ طلایی

The tool definitions from list_tools() map almost one-to-one onto the tools list you send to Claude (name, description, input schema). The wrapper's job is mostly this small conversion.

تعریف ابزارهایی که از list_tools() می‌آید تقریباً یک‌به‌یک با فهرست tools که به Claude می‌فرستی جور است (اسم، توضیح، طرح‌وارهٔ ورودی). کار اصلی لایهٔ واسط همین تبدیل کوچک است.

درس ۶ · Lesson 6

تعریف منابع (Resources)Defining resources

صفحهٔ رسمی ↗

Resources expose data that your app can read, identified by a URI. They come in two shapes:

  • Direct resources have a fixed URI, like docs://documents (the list of all document ids).
  • Templated resources have parameters in the URI, like docs://documents/{doc_id} (one document's contents).

Each resource declares a MIME type (for example application/json or text/plain) so the client knows how to read it.

Why resources and not just another tool? A tool is called when Claude decides. A resource is fetched when your app decides, for example to show a list in the UI or to attach a document the user mentioned, without spending a model turn on it.

منابع (Resources) داده‌ای را ارائه می‌کنند که اپ تو می‌تواند بخواند و هر کدام با یک URI شناخته می‌شوند. دو شکل دارند:

  • منابع مستقیم یک URI ثابت دارند؛ مثل docs://documents (فهرست شناسهٔ همهٔ سندها).
  • منابع قالب‌دار داخل URI پارامتر دارند؛ مثل docs://documents/{doc_id} (محتوای یک سند).

هر منبع یک نوع MIME اعلام می‌کند (مثلاً application/json یا text/plain) تا کلاینت بداند چطور بخواندش.

چرا منبع و نه یک ابزار دیگر؟ ابزار وقتی Claude تصمیم بگیرد صدا زده می‌شود. منبع وقتی اپ تو تصمیم بگیرد خوانده می‌شود؛ مثلاً برای نشان دادن یک فهرست در رابط کاربری یا ضمیمه کردن سندی که کاربر اسمش را آورده، بدون این‌که یک نوبت مدل خرج آن شود.

Think of it like thisمثل این است که…

Tools are asking the chef to cook something (Claude decides). Resources are the waiter grabbing the menu or a bottle of water from the shelf (your app decides): no cooking, just fetching.

ابزارها مثل سفارش دادن یک غذا به آشپز هستند (Claude تصمیم می‌گیرد). منابع مثل برداشتن منو یا یک بطری آب از قفسه توسط گارسون است (اپ تو تصمیم می‌گیرد): پختی در کار نیست، فقط آوردن.

Key wordsواژه‌های کلیدی

Resourceمنبع
داده‌ای که سرور MCP با یک URI در اختیار اپ می‌گذارد تا هر وقت خواست بخواندش.
URI templateقالب URI
نشانی‌ای با جای خالی مثل {doc_id} که با مقدار واقعی پر می‌شود.
MIME typeنوع MIME
برچسبی که نوع داده را مشخص می‌کند؛ مثل text/plain یا application/json.

درس ۷ · Lesson 7

دسترسی به منابعAccessing resources

صفحهٔ رسمی ↗

On the client side you read a resource by its URI and parse it according to its MIME type. The course uses this for a nice feature: when the user types @lease.pdf in the chat, the app fetches that document through the resource and adds its contents to the message before sending it to Claude. Claude can answer immediately, without first calling a read tool.

The app can also use the docs://documents resource to power autocomplete: as the user types @, show the list of available documents.

در سمت کلاینت، یک منبع را با URIاش می‌خوانی و بر اساس نوع MIMEاش تجزیه می‌کنی. دوره از این برای یک قابلیت جالب استفاده می‌کند: وقتی کاربر در گفت‌وگو می‌نویسد @lease.pdf، اپ آن سند را از طریق منبع می‌آورد و محتوایش را قبل از فرستادن به Claude به پیام اضافه می‌کند. Claude بلافاصله می‌تواند جواب بدهد، بدون این‌که اول یک ابزار خواندن را صدا بزند.

اپ می‌تواند از منبع docs://documents برای تکمیل خودکار هم استفاده کند: وقتی کاربر @ را تایپ می‌کند، فهرست سندهای موجود را نشان بده.

Think of it like thisمثل این است که…

It's like a student who brings the right page of the textbook to the teacher's desk along with the question. The teacher doesn't need to go look it up first; the answer comes faster.

مثل دانش‌آموزی است که همراه سؤالش همان صفحهٔ درست کتاب را سر میز معلم می‌آورد. معلم لازم نیست اول برود پیدایش کند؛ جواب سریع‌تر می‌آید.

Pro tipنکتهٔ طلایی

Injecting a resource saves a model turn and tokens, but only inject what's needed. Attaching ten whole documents "just in case" can hide the important one in noise.

تزریق یک منبع یک نوبت مدل و کلی توکن صرفه‌جویی می‌کند، ولی فقط چیزی را تزریق کن که لازم است. ضمیمه کردن ده سند کامل «محض احتیاط» ممکن است سند مهم را در شلوغی گم کند.

۸

درس ۸ · Lesson 8

تعریف پرامپت‌هاDefining prompts

صفحهٔ رسمی ↗

A prompt in MCP is a ready-made, well-tested instruction template that a server offers, with arguments. Users could write "reformat this doc as Markdown" themselves, but a prompt written and tested by the server's authors is usually much better: it knows the right tools to use, the edge cases and the output format.

In the course project, the server offers a format prompt that takes a document id and returns messages telling Claude to rewrite that document in Markdown using the edit tool.

پرامپت در MCP یک قالب دستورالعمل آماده و آزموده است که سرور ارائه می‌کند و آرگومان می‌گیرد. کاربرها می‌توانند خودشان بنویسند «این سند را به Markdown تبدیل کن»، ولی پرامپتی که نویسندگان سرور نوشته و آزموده‌اند معمولاً خیلی بهتر است: ابزارهای درست، حالت‌های خاص و قالب خروجی را می‌شناسد.

در پروژهٔ دوره، سرور یک پرامپت format دارد که شناسهٔ یک سند را می‌گیرد و پیام‌هایی برمی‌گرداند که به Claude می‌گویند آن سند را با ابزار ویرایش، به Markdown بازنویسی کند.

Think of it like thisمثل این است که…

A prompt template is a chef's signature recipe offered on the menu. You could describe a dish yourself, but ordering "the house special" gets you the version the chef has perfected.

قالب پرامپت مثل غذای مخصوص سرآشپز در منوست. می‌توانی خودت یک غذا را توصیف کنی، ولی سفارش «غذای مخصوص» نسخه‌ای را برایت می‌آورد که سرآشپز به کمال رسانده.

Pro tipنکتهٔ طلایی

Good candidates for MCP prompts are tasks your users do often and tend to describe badly: "summarize this ticket for a customer", "turn this doc into release notes", "review this contract with our checklist".

کاندیدهای خوب برای پرامپت‌های MCP کارهایی‌اند که کاربرها زیاد انجام می‌دهند و معمولاً بد توصیفشان می‌کنند: «این تیکت را برای مشتری خلاصه کن»، «این سند را به یادداشت انتشار تبدیل کن»، «این قرارداد را با چک‌لیست ما بررسی کن».

۹

درس ۹ · Lesson 9

پرامپت‌ها در کلاینتPrompts in the client

صفحهٔ رسمی ↗

The client can list the server's prompts and get one with arguments. The result is a list of messages, ready to send to Claude. In the course CLI, prompts appear as slash commands: typing /format menu.md fetches the format prompt with doc_id="menu.md" and sends it, and Claude then reads and edits the document with the server's tools.

So the three building blocks work together in one flow: the user picks a prompt, the app attaches resources, and Claude calls tools.

کلاینت می‌تواند پرامپت‌های سرور را فهرست کند و یکی را با آرگومان‌هایش بگیرد. نتیجه فهرستی از پیام‌هاست که آمادهٔ فرستادن به Claude است. در CLI دوره، پرامپت‌ها به شکل دستورهای اسلشی ظاهر می‌شوند: تایپ /format menu.md پرامپت format را با doc_id="menu.md" می‌گیرد و می‌فرستد و Claude بعد سند را با ابزارهای سرور می‌خواند و ویرایش می‌کند.

پس سه آجر اصلی در یک جریان با هم کار می‌کنند: کاربر یک پرامپت انتخاب می‌کند، اپ منابع را ضمیمه می‌کند و Claude ابزارها را صدا می‌زند.

Think of it like thisمثل این است که…

Slash commands are speed-dial buttons on a phone: one press, and the long, correct number (the full, tested prompt) is dialed for you.

دستورهای اسلشی مثل دکمه‌های شماره‌گیری سریع روی تلفن‌اند: یک بار فشار می‌دهی و شمارهٔ طولانی و درست (پرامپت کامل و آزموده) برایت گرفته می‌شود.

جمع‌بندیWrap-up

۱۰

درس ۱۰ · Lesson 10 Wrap-up · جمع‌بندی

مرور MCPMCP review

صفحهٔ رسمی ↗

The most useful way to remember the three primitives is who controls them:

  • Tools are model-controlled: Claude decides when to call them. Use them for actions and live lookups the model should choose.
  • Resources are app-controlled: your code decides when to fetch them. Use them for data the UI needs or content you attach to messages.
  • Prompts are user-controlled: the user decides when to run them (slash commands, buttons). Use them for ready-made workflows.

When designing a server, ask for each capability: *who should decide when this happens?* The answer tells you which primitive to use. The course ends with a final assessment and a completion badge.

بهترین راه برای به خاطر سپردن سه آجر اصلی این است که بدانی چه کسی کنترلشان می‌کند:

  • ابزارها در کنترل مدل‌اند: Claude تصمیم می‌گیرد کی صدایشان بزند. برای کارها و جست‌وجوهای زنده‌ای که مدل باید انتخاب کند.
  • منابع در کنترل اپ‌اند: کد تو تصمیم می‌گیرد کی بخواندشان. برای داده‌ای که رابط کاربری لازم دارد یا محتوایی که به پیام‌ها ضمیمه می‌کنی.
  • پرامپت‌ها در کنترل کاربرند: کاربر تصمیم می‌گیرد کی اجرایشان کند (دستورهای اسلشی، دکمه‌ها). برای روال‌های آماده.

موقع طراحی یک سرور، برای هر قابلیت بپرس: *چه کسی باید تصمیم بگیرد این کی اتفاق بیفتد؟* جواب به تو می‌گوید از کدام آجر استفاده کنی. دوره با یک آزمون نهایی و نشان پایان دوره تمام می‌شود.

Think of it like thisمثل این است که…

In a restaurant: the chef decides which pans to use (tools, model-controlled), the waiter decides when to bring bread and water (resources, app-controlled), and the customer orders from the menu (prompts, user-controlled).

در یک رستوران: آشپز تصمیم می‌گیرد از کدام تابه استفاده کند (ابزارها، در کنترل مدل)، گارسون تصمیم می‌گیرد کی نان و آب بیاورد (منابع، در کنترل اپ) و مشتری از روی منو سفارش می‌دهد (پرامپت‌ها، در کنترل کاربر).

Key wordsواژه‌های کلیدی

Model-controlledدر کنترل مدل
چیزی که خود مدل تصمیم می‌گیرد کی استفاده‌اش کند (ابزارها).
App-controlledدر کنترل اپ
چیزی که کد اپ تصمیم می‌گیرد کی بخواندش (منابع).
User-controlledدر کنترل کاربر
چیزی که کاربر آگاهانه اجرایش می‌کند (پرامپت‌ها).

خلاصهٔ یک‌نگاهCheat sheet

  • MCP = a standard socket between AI apps and services: servers provide, clients connect.
  • It doesn't replace tool use; it changes who writes and hosts tools.
  • Messages: ListTools / CallTool (also list/read resources, list/get prompts). Transports: stdio or HTTP.
  • FastMCP: @mcp.tool, @mcp.resource("uri"), @mcp.prompt on normal functions; Field(description=…).
  • Test with mcp dev server.py (the inspector).
  • Client: stdio_client → ClientSession → initialize() → list_tools / call_tool / read_resource / get_prompt.
  • Tools = model-controlled · Resources = app-controlled · Prompts = user-controlled.
  • MCP = یک سوکت استاندارد بین اپ‌های هوش مصنوعی و سرویس‌ها: سرورها فراهم می‌کنند، کلاینت‌ها وصل می‌شوند.
  • جایگزین tool use نیست؛ فقط عوض می‌کند چه کسی ابزار را می‌نویسد و میزبانی می‌کند.
  • پیام‌ها: ListTools / CallTool (و فهرست/خواندن منابع، فهرست/گرفتن پرامپت‌ها). روش انتقال: stdio یا HTTP.
  • FastMCP: @mcp.tool، @mcp.resource("uri")، @mcp.prompt روی تابع‌های معمولی؛ Field(description=…).
  • آزمایش با mcp dev server.py (بازرس).
  • کلاینت: stdio_client ← ClientSession ← initialize() ← list_tools / call_tool / read_resource / get_prompt.
  • ابزار = کنترل مدل · منبع = کنترل اپ · پرامپت = کنترل کاربر.
