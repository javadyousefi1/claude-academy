درس ۱ · Lesson 1

دسترسی به APIAccessing the API

صفحهٔ رسمی ↗

What happens when a user types into your app and Claude answers? Five steps:

  1. Your app (web page, mobile app) sends the user's text to your server, never straight to Anthropic, because the request needs your secret API key.
  2. Your server calls the Claude API with the SDK: model name, messages, max_tokens.
  3. The text is split into tokens (small pieces of words) and the model generates the reply one token at a time, each new token predicted from everything before it.
  4. Generation stops when the model is done (end_turn), hits your max_tokens limit, hits a stop sequence, or wants to use a tool.
  5. The API returns the reply plus usage (input and output tokens, which is what you pay for) and a stop_reason.

وقتی کاربر در اپ تو چیزی تایپ می‌کند و Claude جواب می‌دهد، چه اتفاقی می‌افتد؟ پنج قدم:

  1. اپ تو (صفحهٔ وب، اپ موبایل) متن کاربر را به سرور خودت می‌فرستد، نه مستقیم به Anthropic؛ چون درخواست به کلید مخفی API تو نیاز دارد.
  2. سرورت با SDK به Claude API درخواست می‌دهد: اسم مدل، پیام‌ها، max_tokens.
  3. متن به توکن‌ها (تکه‌های کوچک کلمه) شکسته می‌شود و مدل جواب را توکن به توکن تولید می‌کند؛ هر توکن تازه از روی همهٔ چیزهای قبلش پیش‌بینی می‌شود.
  4. تولید وقتی متوقف می‌شود که مدل کارش تمام شده (end_turn)، به سقف max_tokens تو رسیده، به یک دنبالهٔ توقف خورده یا می‌خواهد از ابزاری استفاده کند.
  5. API جواب را همراه با مصرف (توکن‌های ورودی و خروجی؛ همان چیزی که پولش را می‌دهی) و stop_reason (دلیل توقف) برمی‌گرداند.

Think of it like thisمثل این است که…

Your server is the restaurant waiter: customers (the app) never walk into the kitchen (the API) themselves; the waiter carries orders in and dishes out, and only the waiter has the kitchen key.

سرور تو مثل گارسون رستوران است: مشتری‌ها (اپ) هیچ‌وقت خودشان وارد آشپزخانه (API) نمی‌شوند؛ گارسون سفارش را می‌برد و غذا را می‌آورد و فقط او کلید آشپزخانه را دارد.

Watch outحواست باشد

Never put your API key in front-end code (JavaScript in the browser, a mobile app bundle). Anyone can open DevTools, copy it, and spend your money.

هیچ‌وقت کلید API را در کد سمت کاربر نگذار (جاوااسکریپت داخل مرورگر، بستهٔ اپ موبایل). هر کسی می‌تواند DevTools را باز کند، کلید را بردارد و پول تو را خرج کند.

Pro tipنکتهٔ طلایی

Which model? Today's lineup (check the models page for updates): Claude Opus 5.5 (claude-opus-5-5) as the strong default, Claude Sonnet 5.5 for high-volume work, Claude Haiku 5.5 for fast, cheap, simple tasks, and Claude Fable 5.1 when you need the most capable model. Start with the best, then try a cheaper model once you have evals that prove it's good enough.

کدام مدل؟ ردیف فعلی (برای به‌روزرسانی‌ها صفحهٔ مدل‌ها را ببین): Claude Opus 5.5 (claude-opus-5-5) به‌عنوان پیش‌فرض قوی، Claude Sonnet 5.5 برای کارهای پرحجم، Claude Haiku 5.5 برای کارهای ساده، سریع و ارزان، و Claude Fable 5.1 وقتی تواناترین مدل را لازم داری. با بهترین شروع کن، بعد وقتی ارزیابی‌هایی داشتی که ثابت کنند مدل ارزان‌تر کافی است، امتحانش کن.

Key wordsواژه‌های کلیدی

Tokenتوکن
تکهٔ کوچکی از متن (بخشی از یک کلمه) که مدل با آن کار می‌کند و هزینه بر اساس آن حساب می‌شود.

فیلدی در پاسخ API که می‌گوید چرا تولید متن تمام شد.

گرفتن کلید APIGetting an API key

صفحهٔ رسمی ↗

Create a key in the Claude Console (platform.claude.com → API keys). Treat it like a password:

  • Store it in an environment variable named ANTHROPIC_API_KEY, or in a .env file loaded at startup.
  • Add .env to .gitignore before your first commit.
  • Use separate keys (and workspaces) for development and production, and set spend limits in the Console.

یک کلید در کنسول Claude بساز (platform.claude.com ← API keys). مثل رمز عبور با آن رفتار کن:

  • آن را در یک متغیر محیطی به اسم ANTHROPIC_API_KEY یا در یک فایل .env نگه دار که موقع اجرا بارگذاری می‌شود.
  • .env را قبل از اولین کامیت به .gitignore اضافه کن.
  • برای توسعه و محیط واقعی، کلیدها (و فضاهای کاری) جدا داشته باش و در کنسول سقف هزینه بگذار.

Watch outحواست باشد

If a key ever lands in a public repo, revoke it immediately in the Console and create a new one. Deleting the commit is not enough: bots scan GitHub for keys within minutes.

اگر کلیدی حتی یک بار وارد یک مخزن عمومی شد، فوراً در کنسول باطلش کن و کلید تازه بساز. پاک کردن کامیت کافی نیست: ربات‌ها ظرف چند دقیقه گیت‌هاب را برای پیدا کردن کلید می‌گردند.

Think of it like thisمثل این است که…

An API key is your house key: you'd never tape it to the front door (front-end code) or post a photo of it online (a public repo).

کلید API مثل کلید خانه‌ات است: هیچ‌وقت آن را روی در ورودی نمی‌چسبانی (کد سمت کاربر) یا عکسش را در اینترنت نمی‌گذاری (مخزن عمومی).

فرستادن یک درخواستMaking a request

صفحهٔ رسمی ↗

Every request needs three things: model, max_tokens (a safety cap on the reply length, not a target) and messages (a list of {"role": ..., "content": ...} turns, starting with user). The reply's content is a list of blocks: text, and on newer models also thinking blocks or tool calls.

هر درخواست سه چیز لازم دارد: model، max_tokens (سقف ایمنی برای طول جواب، نه هدف) و messages (فهرستی از نوبت‌ها به شکل {"role": ..., "content": ...} که با user شروع می‌شود). content پاسخ یک فهرست از بلوک‌ها است: متن، و در مدل‌های جدیدتر بلوک‌های تفکر یا فراخوانی ابزار هم.

Pro tipنکتهٔ طلایی

Cool tip: the original course reads message.content[0].text. On models where thinking is always on (like Opus 5.5), the first block can be a thinking block, so content[0].text breaks. Always pick blocks by type, as above. Small helper, big headache saved.

نکتهٔ خفن: دورهٔ اصلی message.content[0].text را می‌خواند. روی مدل‌هایی که تفکرشان همیشه روشن است (مثل Opus 5.5)، اولین بلوک ممکن است یک بلوک تفکر باشد؛ پس content[0].text خراب می‌شود. همیشه بلوک‌ها را بر اساس type انتخاب کن، مثل کد بالا. یک تابع کمکی کوچک، یک سردرد بزرگ کمتر.

Think of it like thisمثل این است که…

The request is a form you fill in: who should answer (model), the question (messages) and "reply in at most this many lines" (max_tokens).

درخواست مثل فرمی است که پر می‌کنی: چه کسی جواب بدهد (model)، سؤال چیست (messages) و «حداکثر در این‌قدر خط جواب بده» (max_tokens).

گفت‌وگوهای چندنوبتیMulti-turn conversations

صفحهٔ رسمی ↗

The API is stateless: it remembers nothing between requests. To have a conversation, you keep the history and send all of it every time: user, assistant, user, assistant... Three tiny helpers make this painless.

API بی‌حافظه (stateless) است: بین درخواست‌ها هیچ چیز یادش نمی‌ماند. برای داشتن گفت‌وگو، خودت تاریخچه را نگه می‌داری و هر بار همه‌اش را می‌فرستی: کاربر، دستیار، کاربر، دستیار... سه تابع کمکی کوچک این کار را بی‌دردسر می‌کنند.

Think of it like thisمثل این است که…

Talking to the API is like talking to a goldfish with a notebook: it forgets everything instantly, so before each question you hand it the notebook with the whole conversation so far.

حرف زدن با API مثل حرف زدن با یک ماهی قرمز دفترچه‌به‌دست است: همه‌چیز را فوراً فراموش می‌کند؛ پس قبل از هر سؤال، دفترچه‌ای را که کل گفت‌وگوی تا این‌جا در آن نوشته شده دستش می‌دهی.

Pro tipنکتهٔ طلایی

Long chats get expensive because the whole history is resent each turn. Two fixes from later lessons: prompt caching (pay ~10% for the repeated part) and compaction (the API summarizes old turns for you).

گفت‌وگوهای طولانی گران می‌شوند، چون کل تاریخچه هر نوبت دوباره فرستاده می‌شود. دو راه‌حل از درس‌های بعدی: کش پرامپت (برای بخش تکراری حدود ۱۰٪ هزینه بده) و فشرده‌سازی (compaction) (API خودش نوبت‌های قدیمی را خلاصه می‌کند).

پرامپت‌های سیستمیSystem prompts

صفحهٔ رسمی ↗

The system prompt sets *how* Claude should behave for the whole conversation: its role, tone, rules and format. It's passed separately from messages. A good system prompt describes the job like a briefing for an expert: who the users are, what good help looks like, what to avoid.

پرامپت سیستمی تعیین می‌کند Claude در کل گفت‌وگو *چطور* رفتار کند: نقشش، لحنش، قانون‌هایش و قالب جواب‌هایش. جدا از messages فرستاده می‌شود. یک پرامپت سیستمی خوب، کار را مثل توجیه یک متخصص توصیف می‌کند: کاربرها چه کسانی‌اند، کمک خوب چه شکلی است، از چه چیزی باید دوری کرد.

Think of it like thisمثل این است که…

The system prompt is the job description pinned above the desk; the messages are the customers walking in.

پرامپت سیستمی شرح وظایفی است که بالای میز کار سنجاق شده؛ پیام‌ها مشتری‌هایی هستند که وارد می‌شوند.

Pro tipنکتهٔ طلایی

Explain the why behind rules ("keep answers under 100 words because users read on their phones"). Modern Claude models follow reasons better than SHOUTED RULES, and ALL-CAPS "MUST" language can make them overly rigid.

دلیل پشت قانون‌ها را توضیح بده («جواب‌ها را زیر ۱۰۰ کلمه نگه دار چون کاربرها روی گوشی می‌خوانند»). مدل‌های جدید Claude دلیل را بهتر از قانون‌های فریادزده دنبال می‌کنند و زبان «حتماً» با حروف بزرگ ممکن است آن‌ها را بیش از حد خشک کند.

دما (Temperature)Temperature

صفحهٔ رسمی ↗

When generating each token, the model has a probability for every possible next token. Temperature (0 to 1) reshapes those odds: near 0, it almost always picks the most likely token (predictable, good for extraction); near 1, less likely tokens get a real chance (varied, good for brainstorming).

What changed: the newest models (Opus 5.5, Fable 5.1, Opus 4.7+) reject temperature with a 400 error, and Sonnet 5.5 / Haiku 5.5 reject non-default values. These models are steered by your prompt and the effort setting instead. You can still see temperature at work on models that support it, such as Claude Haiku 4.5.

موقع تولید هر توکن، مدل برای هر توکن ممکنِ بعدی یک احتمال دارد. دما (temperature) (از ۰ تا ۱) این شانس‌ها را تغییر شکل می‌دهد: نزدیک ۰ تقریباً همیشه محتمل‌ترین توکن را انتخاب می‌کند (قابل‌پیش‌بینی؛ خوب برای استخراج داده)؛ نزدیک ۱ توکن‌های کم‌احتمال‌تر هم شانس واقعی پیدا می‌کنند (متنوع؛ خوب برای ایده‌پردازی).

چه چیزی عوض شده: جدیدترین مدل‌ها (Opus 5.5، Fable 5.1، Opus 4.7 به بعد) temperature را با خطای 400 رد می‌کنند و Sonnet 5.5 و Haiku 5.5 مقدارهای غیرپیش‌فرض را رد می‌کنند. این مدل‌ها به جایش با پرامپت تو و تنظیم effort هدایت می‌شوند. هنوز می‌توانی اثر دما را روی مدل‌هایی که پشتیبانی‌اش می‌کنند، مثل Claude Haiku 4.5، ببینی.

Think of it like thisمثل این است که…

Temperature is like a music playlist: at 0 it plays your #1 favorite song every time; at 1 it shuffles and sometimes surprises you. Newer models removed the shuffle knob, so you just ask for the kind of mix you want.

دما مثل فهرست پخش موسیقی است: روی ۰ هر بار آهنگ شمارهٔ یکِ محبوبت را پخش می‌کند؛ روی ۱ قاطی پخش می‌کند و گاهی غافلگیرت می‌کند. مدل‌های جدیدتر دکمهٔ قاطی‌پخش را برداشته‌اند؛ پس فقط بگو چه جور ترکیبی می‌خواهی.

درس ۷ · Lesson 7

پخش زندهٔ پاسخ (Streaming)Response streaming

صفحهٔ رسمی ↗

A long answer can take many seconds. Without streaming, the user stares at a spinner; with streaming, text appears chunk by chunk as it's generated. The SDK's messages.stream() gives you a text_stream for the easy case and the raw events (message_start, content_block_delta, message_stop, ...) when you need them. At the end, get_final_message() returns the complete message to store in your history.

Streaming also matters for reliability: for large max_tokens (roughly above 16K), non-streaming requests can hit HTTP timeouts.

یک جواب طولانی ممکن است چند ثانیه طول بکشد. بدون استریم، کاربر به یک چرخندهٔ انتظار خیره می‌ماند؛ با استریم، متن همان‌طور که تولید می‌شود تکه‌تکه ظاهر می‌شود. messages.stream() در SDK برای حالت ساده یک text_stream می‌دهد و هر وقت لازم داشتی، رویدادهای خام (message_start، content_block_delta، message_stop، ...) را. در پایان، get_final_message() پیام کامل را برمی‌گرداند تا در تاریخچه‌ات ذخیره کنی.

استریم برای پایداری هم مهم است: برای max_tokensهای بزرگ (تقریباً بالای ۱۶ هزار)، درخواست‌های بدون استریم ممکن است به محدودیت زمانی HTTP بخورند.

Think of it like thisمثل این است که…

Without streaming it's like waiting for a whole letter to arrive; with streaming it's a phone call: you hear the words as they're spoken.

بدون استریم مثل منتظر ماندن برای رسیدن یک نامهٔ کامل است؛ با استریم مثل تماس تلفنی است: کلمه‌ها را همان لحظه‌ای که گفته می‌شوند می‌شنوی.

Pro tipنکتهٔ طلایی

In a web app, forward the stream to the browser with Server-Sent Events (SSE), so your server stays the only place that holds the API key.

در یک وب‌اپ، استریم را با Server-Sent Events (SSE) به مرورگر برسان تا سرورت همچنان تنها جایی باشد که کلید API را نگه می‌دارد.

درس ۸ · Lesson 8

دادهٔ ساختاریافتهStructured data

صفحهٔ رسمی ↗

Apps often need pure data (JSON, a code snippet, a CSV row) with no chatty "Here's your JSON!" around it. The original course taught a clever trick: prefill the assistant's reply with an opening code fence (three backticks followed by json) and set the closing fence (three backticks) as a stop sequence, so the output is exactly the JSON.

What changed: prefilling the last assistant turn now returns a 400 error on Opus 4.6+ / Sonnet 4.6+ / Haiku 5.5 and newer. The modern replacement is better anyway: structured outputs, where you give a JSON schema (or a Pydantic model) and the API guarantees valid output.

اپ‌ها اغلب دادهٔ خالص لازم دارند (JSON، یک تکه کد، یک ردیف CSV)، بدون جمله‌های پرحرف مثل «این هم JSON تو!» دورش. دورهٔ اصلی یک ترفند زیرکانه یاد می‌داد: جواب دستیار را با شروع یک بلوک کد (سه بک‌تیک و بعد json) پیش‌پر کن و پایان بلوک (سه بک‌تیک) را دنبالهٔ توقف بگذار تا خروجی دقیقاً همان JSON باشد.

چه چیزی عوض شده: پیش‌پر کردن آخرین نوبت دستیار حالا روی Opus 4.6 به بعد، Sonnet 4.6 به بعد و Haiku 5.5 و جدیدتر خطای 400 می‌دهد. جایگزین امروزی به هر حال بهتر است: خروجی ساختاریافته (structured outputs)؛ یک اسکیمای JSON (یا یک مدل Pydantic) می‌دهی و API خروجی معتبر را تضمین می‌کند.

Pro tipنکتهٔ طلایی

Stop sequences themselves are still useful on every model: e.g. stop_sequences=["</answer>"] to end exactly at a closing tag.

خود دنباله‌های توقف هنوز روی همهٔ مدل‌ها به درد می‌خورند: مثلاً stop_sequences=["</answer>"] تا تولید دقیقاً سر یک تگ پایانی تمام شود.

Think of it like thisمثل این است که…

Prefill was like writing the first words on the answer sheet so the student continues in your format. Structured outputs are a form with fixed boxes: there's simply no space to write anything else.

پیش‌پر کردن مثل این بود که کلمه‌های اول را روی برگهٔ جواب بنویسی تا دانش‌آموز با قالب تو ادامه بدهد. خروجی ساختاریافته یک فرم با خانه‌های ثابت است: اصلاً جایی برای نوشتن چیز دیگری نیست.

Key wordsواژه‌های کلیدی

Prefillپیش‌پر کردن پاسخ
نوشتن شروع جواب دستیار در درخواست تا مدل از همان‌جا ادامه دهد؛ روی مدل‌های جدید پشتیبانی نمی‌شود.
Structured outputsخروجی ساختاریافته
قابلیتی که خروجی را مطابق یک اسکیمای JSON تضمین می‌کند.
Stop sequenceدنبالهٔ توقف
رشته‌ای که وقتی مدل تولیدش کند، تولید همان‌جا متوقف می‌شود.

ارزیابی پرامپتPrompt evaluation

۱۰

درس ۱۰ · Lesson 10

ارزیابی پرامپتPrompt evaluation

صفحهٔ رسمی ↗

After writing a prompt, most people try it once or twice, it looks fine, and they ship it. Then real users send inputs nobody imagined. Prompt evaluation (evals) means testing a prompt systematically: many inputs, an objective score, and a way to compare version A against version B. Prompt engineering improves the prompt; evaluation tells you whether it actually improved.

بیشتر آدم‌ها بعد از نوشتن یک پرامپت، یکی دو بار امتحانش می‌کنند، خوب به نظر می‌رسد و منتشرش می‌کنند. بعد کاربرهای واقعی ورودی‌هایی می‌فرستند که هیچ‌کس تصورش را نکرده بود. ارزیابی پرامپت (eval) یعنی آزمودن پرامپت به‌شکل نظام‌مند: ورودی‌های زیاد، یک نمرهٔ عینی و راهی برای مقایسهٔ نسخهٔ الف با نسخهٔ ب. مهندسی پرامپت پرامپت را بهتر می‌کند؛ ارزیابی به تو می‌گوید واقعاً بهتر شده یا نه.

Think of it like thisمثل این است که…

Trying a prompt twice is like tasting one spoonful and declaring the whole pot perfect. An eval tastes the soup with 50 spoons, from the top, the bottom, and the burnt corner.

دو بار امتحان کردن یک پرامپت مثل این است که یک قاشق بچشی و بگویی کل دیگ عالی است. ارزیابی سوپ را با ۵۰ قاشق می‌چشد؛ از رو، از ته و از گوشهٔ سوخته.

Pro tipنکتهٔ طلایی

Start small: 20 good test cases beat zero. You can grow the set every time a real user finds a bug: each bug becomes a new test case, forever.

کوچک شروع کن: ۲۰ مورد آزمون خوب از صفر بهتر است. هر بار که یک کاربر واقعی باگی پیدا کرد، مجموعه را بزرگ‌تر کن: هر باگ برای همیشه یک مورد آزمون تازه می‌شود.

۱۱

درس ۱۱ · Lesson 11

یک گردش‌کار معمول ارزیابیA typical eval workflow

صفحهٔ رسمی ↗

The loop has five steps:

  1. Draft a prompt.
  2. Create a dataset of test inputs (by hand or generated by Claude).
  3. Run the prompt on every input.
  4. Grade each output (with code, a model, or humans) and average the scores.
  5. Change the prompt, rerun, and compare scores. Keep the version that wins.

این حلقه پنج قدم دارد:

  1. یک پرامپت پیش‌نویس کن.
  2. یک مجموعه‌دادهٔ آزمون از ورودی‌ها بساز (دستی یا با کمک Claude).
  3. پرامپت را روی همهٔ ورودی‌ها اجرا کن.
  4. هر خروجی را نمره بده (با کد، با یک مدل یا با آدم‌ها) و میانگین بگیر.
  5. پرامپت را تغییر بده، دوباره اجرا کن و نمره‌ها را مقایسه کن. نسخهٔ برنده را نگه دار.

Real exampleمثال واقعی

Version 1: "Answer the user's AWS question." → average 6.2/10. Version 2 adds "Answer with exactly one of: Python code, JSON or a regex, and nothing else" → 7.9/10. Without the eval you'd only have a feeling; now you have a number.

نسخهٔ ۱: «به سؤال AWS کاربر جواب بده.» ← میانگین ۶٫۲ از ۱۰. نسخهٔ ۲ اضافه می‌کند «دقیقاً با یکی از این‌ها جواب بده: کد پایتون، JSON یا یک regex، و هیچ چیز دیگر» ← ۷٫۹ از ۱۰. بدون ارزیابی فقط یک حس داشتی؛ حالا یک عدد داری.

Think of it like thisمثل این است که…

It's the science fair method: change one thing, measure, compare to the control.

این همان روش نمایشگاه علمی است: یک چیز را عوض کن، اندازه بگیر، با گروه کنترل مقایسه کن.

درس ۱۲ · Lesson 12

ساختن مجموعه‌دادهٔ آزمونGenerating test datasets

صفحهٔ رسمی ↗

Writing 50 test cases by hand is slow, so ask a fast, cheap model to generate them. Describe the task, ask for variety (easy, tricky, edge cases), and get the cases as JSON. With structured outputs, the dataset arrives already valid.

نوشتن دستی ۵۰ مورد آزمون کند است؛ پس از یک مدل سریع و ارزان بخواه بسازدشان. کار را توصیف کن، تنوع بخواه (آسان، فریبنده، موارد مرزی) و موردها را به شکل JSON بگیر. با خروجی ساختاریافته، مجموعه‌داده از همان اول معتبر می‌رسد.

Watch outحواست باشد

Generated datasets inherit the model's blind spots. Read through them, delete duplicates, and add a few real user inputs by hand.

مجموعه‌داده‌های ساخته‌شده نقطه‌کورهای خود مدل را به ارث می‌برند. بخوانشان، تکراری‌ها را پاک کن و چند ورودی واقعی کاربر را دستی اضافه کن.

۱۳

درس ۱۳ · Lesson 13

اجرای ارزیابیRunning the eval

صفحهٔ رسمی ↗

The runner is a simple loop: for each test case, merge the case into your prompt template, call Claude, grade the output, and store {case, output, score}. At the end, print the average score. Keep the code boring and the results saved to a file, so you can compare runs later.

اجراکننده یک حلقهٔ ساده است: برای هر مورد آزمون، مورد را داخل قالب پرامپتت بگذار، Claude را صدا بزن، خروجی را نمره بده و {case, output, score} را ذخیره کن. در پایان میانگین نمره را چاپ کن. کد را ساده و حوصله‌سربر نگه دار و نتیجه‌ها را در یک فایل ذخیره کن تا بعداً اجراها را مقایسه کنی.

Pro tipنکتهٔ طلایی

Run the cases in parallel (threads or async) once the loop works; 50 sequential calls are slow. And for big nightly evals, the Message Batches API costs about half price.

وقتی حلقه درست کار کرد، موردها را موازی اجرا کن (با threadها یا async)؛ ۵۰ فراخوانی پشت سر هم کند است. برای ارزیابی‌های بزرگ شبانه هم Message Batches API تقریباً نصف قیمت درمی‌آید.

درس ۱۴ · Lesson 14

نمره‌دهی با مدلModel-based grading

صفحهٔ رسمی ↗

Some qualities (helpfulness, correctness of reasoning, tone) are hard to check with code, so a grader model scores them. A good grader prompt asks for strengths, weaknesses and reasoning first, then a score (1-10), because a score written before reasoning tends to be arbitrary. Structured outputs keep the grade machine-readable.

بعضی کیفیت‌ها (مفید بودن، درستی استدلال، لحن) با کد سخت سنجیده می‌شوند؛ پس یک مدل نمره‌دهنده نمره‌شان می‌دهد. یک پرامپت نمره‌دهی خوب اول نقطه‌های قوت، نقطه‌های ضعف و استدلال را می‌خواهد، بعد نمره (۱ تا ۱۰)؛ چون نمره‌ای که قبل از استدلال نوشته شود معمولاً دلبخواهی است. خروجی ساختاریافته نمره را برای ماشین قابل‌خواندن نگه می‌دارد.

Watch outحواست باشد

Graders can be biased (for example, toward longer answers). Spot-check a sample of grades by hand, and give the grader a rubric with concrete criteria.

نمره‌دهنده‌ها ممکن است سوگیری داشته باشند (مثلاً به نفع جواب‌های طولانی‌تر). نمونه‌ای از نمره‌ها را دستی چک کن و به نمره‌دهنده یک روبریک با معیارهای مشخص بده.

Think of it like thisمثل این است که…

A model grader is a teaching assistant with a rubric: fast and consistent, but the professor still checks some papers.

نمره‌دهندهٔ مدلی مثل دستیار آموزشی با روبریک است: سریع و یکنواخت، ولی استاد هنوز چند برگه را خودش چک می‌کند.

۱۵

درس ۱۵ · Lesson 15

نمره‌دهی با کدCode-based grading

صفحهٔ رسمی ↗

Whatever *can* be checked by code *should* be: it's free, fast and perfectly consistent. Typical checks: is the JSON valid (json.loads)? Does the Python parse (ast.parse)? Does the regex compile (re.compile)? Is the answer under 100 words? Combine a code score with the model score for a fuller picture.

هر چیزی که *می‌شود* با کد چک کرد، *باید* با کد چک شود: رایگان، سریع و کاملاً یکنواخت است. چک‌های معمول: JSON معتبر است (json.loads)؟ کد پایتون تجزیه می‌شود (ast.parse)؟ regex کامپایل می‌شود (re.compile)؟ جواب زیر ۱۰۰ کلمه است؟ برای تصویر کامل‌تر، نمرهٔ کد را با نمرهٔ مدل ترکیب کن.

Pro tipنکتهٔ طلایی

Code graders catch regressions instantly: if a prompt change makes 3 of 50 outputs invalid JSON, you'll know before your users do.

نمره‌دهنده‌های کدی پسرفت‌ها را فوراً می‌گیرند: اگر یک تغییر پرامپت باعث شود ۳ خروجی از ۵۰ خروجی JSON نامعتبر شوند، قبل از کاربرهایت خبردار می‌شوی.

تکنیک‌های مهندسی پرامپتPrompt engineering techniques

۱۷

درس ۱۷ · Lesson 17

مهندسی پرامپتPrompt engineering

صفحهٔ رسمی ↗

Prompt engineering is improving a prompt step by step, with an eval as your scoreboard: set a goal, write a first prompt, measure it, apply one technique, measure again. The running example in this section is a prompt that creates a one-day meal plan for an athlete from their height, weight, goal and dietary restrictions. A naive first version scores poorly; each technique below raises the score.

مهندسی پرامپت یعنی بهتر کردن پرامپت قدم به قدم، با یک ارزیابی به‌عنوان تابلوی امتیاز: هدف بگذار، اولین پرامپت را بنویس، اندازه‌اش بگیر، یک تکنیک را اعمال کن، دوباره اندازه بگیر. مثال سراسری این بخش پرامپتی است که از روی قد، وزن، هدف و محدودیت‌های غذایی یک ورزشکار، برنامهٔ غذایی یک‌روزه می‌سازد. نسخهٔ اول ساده‌لوحانه نمرهٔ کمی می‌گیرد؛ هر تکنیک زیر نمره را بالا می‌برد.

Think of it like thisمثل این است که…

It's like tuning a guitar with a tuner: you don't guess, you adjust one string and watch the needle.

مثل کوک کردن گیتار با دستگاه تیونر است: حدس نمی‌زنی؛ یک سیم را تنظیم می‌کنی و عقربه را نگاه می‌کنی.

درس ۱۸ · Lesson 18

روشن و مستقیم بودنBeing clear and direct

صفحهٔ رسمی ↗

The first line of a prompt matters most. Open with a clear action verb and the exact task: not "What should this person eat?" but "Generate a one-day meal plan for an athlete that meets their dietary restrictions." Claude should know from line one what it's producing.

خط اول پرامپت از همه مهم‌تر است. با یک فعل عملی روشن و خود کار دقیق شروع کن: نه «این آدم چه بخورد؟»، بلکه «برای یک ورزشکار یک برنامهٔ غذایی یک‌روزه بساز که محدودیت‌های غذایی‌اش را رعایت کند.» Claude باید از همان خط اول بداند چه چیزی تولید می‌کند.

Sample promptپرامپت نمونه

Generate a one-day meal plan for an athlete that meets their dietary restrictions.

برای یک ورزشکار یک برنامهٔ غذایی یک‌روزه بساز که محدودیت‌های غذایی‌اش را رعایت کند.

Pro tipنکتهٔ طلایی

Test: if you showed only the first sentence to a smart colleague, would they know what to deliver? If not, rewrite it.

آزمون: اگر فقط جملهٔ اول را به یک همکار باهوش نشان بدهی، می‌فهمد چه چیزی باید تحویل بدهد؟ اگر نه، بازنویسی‌اش کن.

۱۹

درس ۱۹ · Lesson 19

مشخص بودنBeing specific

صفحهٔ رسمی ↗

Add guidelines. Two kinds help most:

  • Qualities of the output: length, format, what to include (e.g., total calories, protein per meal, a shopping list).
  • Steps to follow: the process Claude should use (e.g., "first estimate daily calories, then split them across meals, then check every item against the restrictions").

Specific guidelines usually produce the biggest jump in eval score.

رهنمود اضافه کن. دو نوعش بیشتر از همه کمک می‌کند:

  • ویژگی‌های خروجی: طول، قالب، چه چیزهایی باشد (مثلاً کالری کل، پروتئین هر وعده، فهرست خرید).
  • قدم‌هایی که باید دنبال شود: فرایندی که Claude باید به کار ببرد (مثلاً «اول کالری روزانه را تخمین بزن، بعد بین وعده‌ها تقسیمش کن، بعد هر قلم را با محدودیت‌ها چک کن»).

رهنمودهای مشخص معمولاً بیشترین جهش را در نمرهٔ ارزیابی ایجاد می‌کنند.

Think of it like thisمثل این است که…

"Make me a cake" vs "a chocolate cake for 8 people, not too sweet, ready by 6 pm": the second baker can't really get it wrong.

«برایم کیک درست کن» در برابر «یک کیک شکلاتی برای ۸ نفر، نه خیلی شیرین، تا ساعت ۶ عصر»: نانوای دوم واقعاً نمی‌تواند اشتباه کند.

درس ۲۰ · Lesson 20

ساختاردهی با تگ‌های XMLStructure with XML tags

صفحهٔ رسمی ↗

When a prompt contains data (athlete info, a long document, sales records), wrap each piece in XML-style tags like <athlete_information> or <sales_records>. Tags separate *instructions* from *content*, make clear what each block is, and let you refer to them ("using the data in <sales_records>..."). The tag names don't need to be special; descriptive is enough.

وقتی پرامپت داده دارد (اطلاعات ورزشکار، یک سند طولانی، سوابق فروش)، هر تکه را در تگ‌هایی به سبک XML بپیچان، مثل <athlete_information> یا <sales_records>. تگ‌ها *دستور* را از *محتوا* جدا می‌کنند، روشن می‌کنند هر بلوک چیست و اجازه می‌دهند به آن‌ها ارجاع بدهی («با استفاده از داده‌های داخل <sales_records>...»). اسم تگ‌ها لازم نیست خاص باشد؛ توصیفی بودن کافی است.

Think of it like thisمثل این است که…

XML tags are labeled boxes when moving house: "KITCHEN – fragile" tells everyone what's inside without opening it.

تگ‌های XML مثل جعبه‌های برچسب‌دار موقع اسباب‌کشی هستند: «آشپزخانه – شکستنی» به همه می‌گوید داخلش چیست، بدون باز کردنش.

Pro tipنکتهٔ طلایی

Put long documents first and your question at the end. With very long context, a question placed after the material usually gets better answers.

سندهای طولانی را اول و سؤالت را در آخر بگذار. در زمینه‌های خیلی طولانی، سؤالی که بعد از مطالب می‌آید معمولاً جواب‌های بهتری می‌گیرد.

درس ۲۱ · Lesson 21

آوردن مثالProviding examples

صفحهٔ رسمی ↗

Examples are one of the strongest tools you have. One-shot = one example; multi-shot = several. Wrap them in tags such as <sample_input> and <ideal_output>, include tricky cases (sarcasm in a sentiment task, an empty field in an extraction task), and say why the example is good. A great trick: take the highest-scoring output from your eval and use it as the example.

مثال یکی از قوی‌ترین ابزارهای توست. تک‌مثالی (one-shot) = یک مثال؛ چندمثالی (multi-shot) = چند مثال. آن‌ها را در تگ‌هایی مثل <sample_input> و <ideal_output> بپیچان، موردهای فریبنده را هم بیاور (کنایه در یک کار تشخیص احساس، یک فیلد خالی در یک کار استخراج) و بگو مثال چرا خوب است. یک ترفند عالی: بهترین خروجی ارزیابی‌ات را بردار و به‌عنوان مثال استفاده کن.

Watch outحواست باشد

Claude copies examples closely. If all your examples are about running, the meal plans may all become runner-ish. Vary them, or say "these are illustrations, not templates".

Claude مثال‌ها را از نزدیک تقلید می‌کند. اگر همهٔ مثال‌هایت دربارهٔ دویدن باشند، شاید همهٔ برنامه‌های غذایی دونده‌مآب شوند. تنوعشان بده یا بگو «این‌ها نمونه‌اند، نه قالب».

Think of it like thisمثل این است که…

Showing an example is like showing a photo to the barber: a hundred words about "short on the sides" can't beat one picture.

نشان دادن مثال مثل نشان دادن عکس به آرایشگر است: صد کلمه دربارهٔ «کناره‌ها کوتاه» به پای یک عکس نمی‌رسد.

۲۳

درس ۲۳ · Lesson 23

آشنایی با استفاده از ابزارIntroducing tool use

صفحهٔ رسمی ↗

Claude only knows its training data and what's in the prompt. It can't check today's weather, read your database or send an email, unless you give it tools. The flow:

  1. You send the user's message plus tool definitions (name, description, input schema).
  2. Claude decides a tool would help and replies with a tool_use block: the tool name and arguments.
  3. Your code runs the real function.
  4. You send back a tool_result.
  5. Claude uses the result to write its final answer (or asks for another tool).

Claude فقط دادهٔ آموزشی‌اش و چیزی را که داخل پرامپت است می‌شناسد. نمی‌تواند هوای امروز را چک کند، پایگاه‌دادهٔ تو را بخواند یا ایمیل بفرستد، مگر این‌که به آن ابزار بدهی. جریان کار:

  1. پیام کاربر را همراه با تعریف ابزارها (اسم، توضیح، اسکیمای ورودی) می‌فرستی.
  2. Claude تصمیم می‌گیرد یک ابزار کمک می‌کند و با یک بلوک tool_use جواب می‌دهد: اسم ابزار و آرگومان‌ها.
  3. کد تو تابع واقعی را اجرا می‌کند.
  4. یک tool_result برمی‌گردانی.
  5. Claude با آن نتیجه جواب نهایی‌اش را می‌نویسد (یا ابزار دیگری می‌خواهد).

Think of it like thisمثل این است که…

Claude is a brilliant manager with no hands: it decides "call the warehouse and check stock", but your code is the assistant who actually picks up the phone and reports back.

Claude مثل یک مدیر باهوش بی‌دست است: تصمیم می‌گیرد «به انبار زنگ بزن و موجودی را چک کن»، ولی کد تو همان دستیاری است که واقعاً تلفن را برمی‌دارد و خبر می‌آورد.

Key wordsواژه‌های کلیدی

Tool useاستفاده از ابزار
قابلیتی که Claude با آن درخواست اجرای تابع‌های تعریف‌شده را می‌دهد و نتیجه را در جوابش به کار می‌برد.
tool_resultنتیجهٔ ابزار
بلوکی که خروجی اجرای ابزار را به Claude برمی‌گرداند.

درس ۲۴ · Lesson 24

معرفی پروژهProject overview

صفحهٔ رسمی ↗

The section builds a small assistant that can set reminders: "Remind me to renew my passport in 3 weeks." To do that, Claude needs tools it doesn't have: get the current date and time, add a duration to a date, and set a reminder. You'll write the functions, describe them with schemas, and run the loop that lets Claude chain them.

این بخش یک دستیار کوچک می‌سازد که می‌تواند یادآوری تنظیم کند: «سه هفتهٔ دیگر یادم بینداز گذرنامه‌ام را تمدید کنم.» برای این کار Claude ابزارهایی لازم دارد که ندارد: گرفتن تاریخ و ساعت فعلی، اضافه کردن یک مدت به یک تاریخ و ثبت یادآوری. تابع‌ها را می‌نویسی، با اسکیما توصیفشان می‌کنی و حلقه‌ای را اجرا می‌کنی که به Claude اجازه می‌دهد آن‌ها را پشت هم صدا بزند.

Pro tipنکتهٔ طلایی

Why does Claude need a clock tool? Its knowledge has a cutoff and it can't see your computer's clock. Without the tool, "in 3 weeks" from *when*? It would have to guess.

چرا Claude ابزار ساعت لازم دارد؟ دانشش تاریخ برش دارد و ساعت کامپیوتر تو را نمی‌بیند. بدون این ابزار، «سه هفتهٔ دیگر» از *کِی*؟ مجبور است حدس بزند.

۲۵

درس ۲۵ · Lesson 25

تابع‌های ابزارTool functions

صفحهٔ رسمی ↗

A tool function is a normal function your code runs. Good tool functions have descriptive names and arguments, validate inputs, and raise clear error messages, because the error text goes back to Claude, which can then correct itself and try again.

تابع ابزار یک تابع معمولی است که کد تو اجرایش می‌کند. تابع‌های ابزار خوب اسم و آرگومان توصیفی دارند، ورودی را اعتبارسنجی می‌کنند و پیام خطای روشن می‌دهند؛ چون متن خطا به Claude برمی‌گردد و او می‌تواند خودش را اصلاح کند و دوباره امتحان کند.

Think of it like thisمثل این است که…

A good error message is like a GPS saying "recalculating: turn left at the next street" instead of just beeping.

یک پیام خطای خوب مثل مسیریابی است که می‌گوید «در حال محاسبهٔ دوباره: در خیابان بعدی به چپ بپیچ»، به جای این‌که فقط بوق بزند.

۲۶

درس ۲۶ · Lesson 26

اسکیمای ابزارهاTool schemas

صفحهٔ رسمی ↗

Claude never sees your Python. It sees a schema: name, description and input_schema (JSON Schema for the arguments). The description is the most important part: 3–4 sentences on what the tool does, when to use it, and what it returns. Each parameter gets its own description too. Tip from the course: ask Claude to write the schema for your function, then review it.

Claude هیچ‌وقت کد پایتون تو را نمی‌بیند. یک اسکیما می‌بیند: name، description و input_schema (اسکیمای JSON برای آرگومان‌ها). توضیح مهم‌ترین بخش است: ۳ تا ۴ جمله دربارهٔ این‌که ابزار چه می‌کند، کی باید استفاده شود و چه برمی‌گرداند. هر پارامتر هم توضیح خودش را می‌گیرد. نکتهٔ دوره: از Claude بخواه برای تابعت اسکیما بنویسد، بعد بازبینی‌اش کن.

Pro tipنکتهٔ طلایی

Cool tip: add "strict": True (with additionalProperties: false) and the API guarantees the arguments match your schema: no missing fields, no wrong types. And write the description prescriptively ("Call this whenever...") because recent models decide when to call tools from it.

نکتهٔ خفن: "strict": True را اضافه کن (همراه با additionalProperties: false) تا API تضمین کند آرگومان‌ها با اسکیمایت جورند: بدون فیلد جاافتاده، بدون نوع اشتباه. و توضیح را دستوری بنویس («هر وقت ... صدایش بزن»)، چون مدل‌های جدید از روی آن تصمیم می‌گیرند کی ابزار را صدا بزنند.

Think of it like thisمثل این است که…

The schema is the menu description, not the recipe: the diner (Claude) decides what to order from the description alone.

اسکیما توضیح منوی رستوران است، نه دستور پخت: مشتری (Claude) فقط از روی توضیح تصمیم می‌گیرد چه سفارش بدهد.

۲۷

درس ۲۷ · Lesson 27

کار با بلوک‌های پیامHandling message blocks

صفحهٔ رسمی ↗

When Claude wants a tool, its reply contains multiple blocks: often a short text ("Let me check the date") and one or more tool_use blocks, each with an id, name and input. Two rules: append the entire response.content to your history as the assistant turn (not just the text), and check stop_reason == "tool_use" to know tools are waiting.

وقتی Claude ابزاری می‌خواهد، جوابش چند بلوک دارد: اغلب یک متن کوتاه («بگذار تاریخ را چک کنم») و یک یا چند بلوک tool_use که هر کدام id، name و input دارند. دو قانون: کل response.content را به‌عنوان نوبت دستیار به تاریخچه اضافه کن (نه فقط متن را)، و stop_reason == "tool_use" را چک کن تا بفهمی ابزارها منتظرند.

Watch outحواست باشد

If you keep only the text and drop the tool_use block, your next request breaks: every tool_result must point to a tool_use id that exists in the previous assistant turn.

اگر فقط متن را نگه داری و بلوک tool_use را بیندازی، درخواست بعدی‌ات خراب می‌شود: هر tool_result باید به شناسهٔ یک tool_use اشاره کند که در نوبت قبلی دستیار وجود دارد.

۲۸

درس ۲۸ · Lesson 28

فرستادن نتیجهٔ ابزارSending tool results

صفحهٔ رسمی ↗

Run the function, then send a user message containing a tool_result block for each tool_use: its tool_use_id, the output as content, and is_error: True if it failed. Claude reads the result and continues.

تابع را اجرا کن، بعد یک پیام کاربر بفرست که برای هر tool_use یک بلوک tool_result دارد: tool_use_id آن، خروجی به‌عنوان content، و اگر شکست خورد is_error: True. Claude نتیجه را می‌خواند و ادامه می‌دهد.

Think of it like thisمثل این است که…

tool_use_id is the ticket number at a deli counter: when your order is ready, they call *your* number, so nothing gets mixed up.

tool_use_id مثل شمارهٔ نوبت پشت پیشخوان اغذیه‌فروشی است: وقتی سفارشت آماده شد، *شمارهٔ تو* را صدا می‌زنند تا چیزی قاطی نشود.

۲۹

درس ۲۹ · Lesson 29

گفت‌وگوهای چندنوبتی با ابزارMulti-turn conversations with tools

صفحهٔ رسمی ↗

Real requests often need several tool calls in a row. "Set a reminder for my doctor's appointment 177 days from today" → Claude calls get_current_datetime, then add_duration_to_datetime with that date, then set_reminder with the result, then answers. Each round trip is: Claude asks → you run → you send results → Claude continues, until stop_reason is no longer "tool_use".

درخواست‌های واقعی اغلب چند فراخوانی ابزار پشت سر هم لازم دارند. «برای نوبت دکترم ۱۷۷ روز بعد از امروز یادآوری بگذار» ← Claude اول get_current_datetime را صدا می‌زند، بعد add_duration_to_datetime را با آن تاریخ، بعد set_reminder را با نتیجه، و بعد جواب می‌دهد. هر رفت‌وبرگشت این است: Claude می‌خواهد ← تو اجرا می‌کنی ← نتیجه را می‌فرستی ← Claude ادامه می‌دهد؛ تا وقتی stop_reason دیگر "tool_use" نباشد.

Think of it like thisمثل این است که…

It's like a treasure hunt: each clue (tool result) tells Claude where to go next, until it reaches the treasure (the final answer).

مثل گنج‌یابی است: هر سرنخ (نتیجهٔ ابزار) به Claude می‌گوید بعدش کجا برود، تا به گنج (جواب نهایی) برسد.

۳۰

درس ۳۰ · Lesson 30

پیاده‌سازی چند نوبتImplementing multiple turns

صفحهٔ رسمی ↗

Put the round trips in a loop. The loop ends when Claude stops asking for tools. Today the SDK also offers a tool runner (beta) that runs this loop for you, generating schemas from typed Python functions. Know both: the manual loop teaches how things work; the runner saves code.

رفت‌وبرگشت‌ها را در یک حلقه بگذار. حلقه وقتی تمام می‌شود که Claude دیگر ابزار نخواهد. امروز SDK یک اجراکنندهٔ ابزار (tool runner) (بتا) هم دارد که این حلقه را برایت اجرا می‌کند و اسکیماها را از تابع‌های پایتونِ نوع‌دار می‌سازد. هر دو را بلد باش: حلقهٔ دستی نشان می‌دهد چیزها چطور کار می‌کنند؛ اجراکننده کد را کم می‌کند.

Watch outحواست باشد

Always add a safety limit (e.g., max 20 iterations) to hand-written loops. A confused agent calling the same tool forever is a real, expensive bug.

به حلقه‌های دست‌نویس همیشه یک سقف ایمنی اضافه کن (مثلاً حداکثر ۲۰ دور). ایجنت گیج‌شده‌ای که تا ابد یک ابزار را صدا می‌زند، یک باگ واقعی و گران است.

درس ۳۱ · Lesson 31

استفاده از چند ابزار (و ابزار دسته‌ای)Using multiple tools (and the batch tool)

صفحهٔ رسمی ↗

Give Claude several tools and it picks the right one per step. When steps are independent, Claude can request several tools in one response (parallel tool use): for example, two set_reminder calls at once. Run them all and return all the results in one user message. Older courses taught a "batch tool" workaround (a tool that takes a list of other tool calls) to encourage this; current models do parallel calls natively. To force one call at a time, set tool_choice={"type": "auto", "disable_parallel_tool_use": True}.

به Claude چند ابزار بده تا در هر قدم ابزار درست را انتخاب کند. وقتی قدم‌ها مستقل‌اند، Claude می‌تواند در یک جواب چند ابزار را درخواست کند (استفادهٔ موازی): مثلاً دو فراخوانی set_reminder با هم. همه را اجرا کن و همهٔ نتیجه‌ها را در یک پیام کاربر برگردان. دوره‌های قدیمی‌تر یک راه‌حل «ابزار دسته‌ای» (ابزاری که فهرستی از فراخوانی‌های ابزارهای دیگر را می‌گیرد) یاد می‌دادند تا این کار تشویق شود؛ مدل‌های فعلی فراخوانی موازی را خودشان انجام می‌دهند. برای اجبار به یک فراخوانی در هر نوبت، tool_choice={"type": "auto", "disable_parallel_tool_use": True} بگذار.

Real exampleمثال واقعی

فراخوانی ریزدانهٔ ابزار (استریم ورودی ابزار)Fine-grained tool calling

صفحهٔ رسمی ↗

When you stream a response that calls a tool, the tool's arguments arrive as input_json_delta events: pieces of JSON. Pro tipنکتهٔ طلایی

This is how coding agents show a file being written live. For a short {"city": "Paris"} input you'll never notice the difference; for a 5,000-line file you will.

You want Claude to answer questions about an 800-page manual. Option 1: paste the whole thing into every request. Simple, but slow and expensive per question, and impossible once you have thousands of documents. Option 2: RAG. RAG costs more engineering (chunking, search, ranking) but scales to huge libraries and keeps each request small.

راهبردهای تکه‌کردن متنText chunking strategies

صفحهٔ رسمی ↗

How you split documents shapes the whole system: bad chunks feed irrelevant or half-sentences into the prompt. Three strategies:

  • Size-based: every N characters, with some overlap so sentences cut at a border appear in both chunks. Works on any text.
  • Structure-based: split on headings or sections (e.g., Markdown ##). Great chunks, but only when the document has reliable structure.
  • Sentence-based: group a few whole sentences per chunk. A good middle ground.

این‌که سندها را چطور تقسیم کنی، کل سیستم را شکل می‌دهد: تکه‌های بد، متن نامربوط یا نصفه‌جمله را وارد پرامپت می‌کنند. سه راهبرد:

  • بر اساس اندازه: هر N کاراکتر، با کمی هم‌پوشانی تا جمله‌هایی که سر مرز بریده می‌شوند در هر دو تکه بیایند. روی هر متنی کار می‌کند.
  • بر اساس ساختار: تقسیم روی سرتیترها یا بخش‌ها (مثلاً ## در Markdown). تکه‌های عالی می‌دهد، ولی فقط وقتی سند ساختار قابل‌اعتمادی دارد.
  • بر اساس جمله: چند جملهٔ کامل در هر تکه. یک حد وسط خوب.

Think of it like thisمثل این است که…

Chunking is cutting a pizza: cut randomly and some slices are all crust; cut along the lines and every slice has toppings.

تکه‌کردن مثل بریدن پیتزا است: اگر شانسی ببری، بعضی تکه‌ها فقط نان‌اند؛ اگر از روی خط‌ها ببری، هر تکه مواد دارد.

embeddingها مختصات روی نقشهٔ معنا هستند: «سگ» و «توله‌سگ» در یک خیابان زندگی می‌کنند، «کاربراتور» در شهر دیگری است.

جریان کامل RAGThe full RAG flow

صفحهٔ رسمی ↗

Two phases:

  • Indexing (once): chunk documents → embed each chunk → store vectors (in a vector database).
  • Answering (per question): embed the question → find the chunks with the most similar vectors (usually cosine similarity) → put the top few into the prompt → Claude answers from them.

Cosine similarity measures the angle between two vectors: 1 means "pointing the same way" (very similar), 0 means unrelated.

دو مرحله:

  • نمایه‌سازی (یک بار): سندها را تکه کن ← هر تکه را embed کن ← بردارها را ذخیره کن (در یک پایگاه‌دادهٔ برداری).
  • پاسخ دادن (برای هر سؤال): سؤال را embed کن ← تکه‌هایی را که بردارشان شبیه‌تر است پیدا کن (معمولاً با شباهت کسینوسی) ← چند تکهٔ برتر را در پرامپت بگذار ← Claude بر اساس آن‌ها جواب می‌دهد.

شباهت کسینوسی زاویهٔ بین دو بردار را می‌سنجد: ۱ یعنی «به یک سمت اشاره می‌کنند» (خیلی شبیه)، ۰ یعنی بی‌ربط.

Step by stepقدم‌به‌قدم

  1. Chunk the documents.
  2. Embed every chunk and store the vectors.
  3. Embed the user's question.
  4. Rank chunks by cosine similarity; keep the top 3-5.
  5. Send question + chunks to Claude with "answer only from the context".
  1. سندها را تکه کن.
  2. همهٔ تکه‌ها را embed کن و بردارها را ذخیره کن.
  3. سؤال کاربر را embed کن.
  4. تکه‌ها را با شباهت کسینوسی رتبه‌بندی کن؛ ۳ تا ۵ تای برتر را نگه دار.
  5. سؤال و تکه‌ها را با «فقط از روی زمینه جواب بده» برای Claude بفرست.

Think of it like thisمثل این است که…

It's a librarian with a great memory for topics: you ask a question, they walk straight to the right three shelves.

مثل کتابداری است که حافظهٔ عالی برای موضوع‌ها دارد: سؤالی می‌پرسی و او مستقیم به سمت سه قفسهٔ درست می‌رود.

Cosine similarityشباهت کسینوسی

جست‌وجوی واژگانی BM25BM25 lexical search

صفحهٔ رسمی ↗

Semantic search is great at meaning but weak at exact terms: an incident ID like INC-2023-Q4-011, a product code, a rare name. BM25 is a classic keyword ranking method: it scores chunks that contain the query's words, giving extra weight to rare words (an ID that appears once matters more than "the"). Use both kinds of search together.

BM25 یک روش کلاسیک رتبه‌بندی کلیدواژه‌ای است: به تکه‌هایی که کلمه‌های سؤال را دارند امتیاز می‌دهد و به کلمه‌های کمیاب وزن بیشتری می‌دهد (شناسه‌ای که فقط یک بار آمده، از «the» مهم‌تر است). هر دو نوع جست‌وجو را با هم به کار ببر.

Semantic search is a friend who understands what you mean; BM25 is a friend who remembers exact phone numbers. You want both at the party.

جست‌وجوی معنایی دوستی است که منظورت را می‌فهمد؛ BM25 دوستی است که شماره‌تلفن‌ها را دقیق یادش می‌ماند. هر دو را در مهمانی می‌خواهی.

یک خط لولهٔ RAG چندنمایه‌ایA multi-index RAG pipeline

صفحهٔ رسمی ↗

Wrap the vector index and the BM25 index in one Retriever that queries both and merges the two ranked lists with reciprocal rank fusion (RRF): each chunk gets 1 / (k + rank) from each list (k is usually 60), and the sums decide the final order. Chunks ranked well by both methods rise to the top. This "hybrid search" is a strong default for real RAG systems.

نمایهٔ برداری و نمایهٔ BM25 را در یک بازیاب (Retriever) بپیچان که از هر دو می‌پرسد و دو فهرست رتبه‌بندی‌شده را با ادغام رتبهٔ معکوس (RRF) یکی می‌کند: هر تکه از هر فهرست 1 / (k + rank) امتیاز می‌گیرد (k معمولاً ۶۰ است) و جمع امتیازها ترتیب نهایی را تعیین می‌کند. تکه‌هایی که در هر دو روش رتبهٔ خوبی دارند به بالا می‌آیند. این «جست‌وجوی ترکیبی» یک پیش‌فرض قوی برای سیستم‌های RAG واقعی است.

Pro tipنکتهٔ طلایی

Two upgrades covered in the Bedrock and Vertex versions of this course: reranking (ask Claude to reorder the top 10 candidates by relevance) and contextual retrieval (before indexing, ask Claude to write a one-line context for each chunk, like "This chunk is from the Q4 security report, section on incidents", and embed that with the chunk).

دو ارتقا که در نسخه‌های Bedrock و Vertex همین دوره آمده: رتبه‌بندی دوباره (reranking) (از Claude بخواه ۱۰ کاندیدای برتر را بر اساس ارتباط دوباره مرتب کند) و بازیابی زمینه‌دار (contextual retrieval) (قبل از نمایه‌سازی، از Claude بخواه برای هر تکه یک خط زمینه بنویسد، مثل «این تکه از گزارش امنیتی فصل چهارم، بخش رخدادهاست» و آن را همراه تکه embed کن).

Think of it like thisمثل این است که…

RRF is like combining two judges' rankings at a talent show: a contestant both judges liked beats one only a single judge adored.

RRF مثل ترکیب رتبه‌بندی دو داور در یک مسابقهٔ استعدادیابی است: شرکت‌کننده‌ای که هر دو داور دوستش داشتند، از کسی که فقط یک داور عاشقش بود جلو می‌زند.

صفحهٔ رسمی ↗

Thinking tokens are billed as output tokens, so higher effort = better answers on hard tasks, at higher cost and latency.

کش پرامپتPrompt caching

صفحهٔ رسمی ↗

Every request makes Claude process the whole prompt from scratch, even if 95% of it (a long system prompt, a big document, tool definitions) is the same as last time. Prompt caching saves the processed prefix for a while, so the next request that starts with the same bytes reuses it: cache reads cost about a tenth of normal input (even less on some newest models) and come back faster. Writing to the cache costs a bit more (1.25× for the default 5-minute cache, 2× for the 1-hour option).

هر درخواست باعث می‌شود Claude کل پرامپت را از صفر پردازش کند، حتی اگر ۹۵٪ آن (یک پرامپت سیستمی طولانی، یک سند بزرگ، تعریف ابزارها) با دفعهٔ قبل یکی باشد. کش پرامپت پیشوند پردازش‌شده را مدتی نگه می‌دارد تا درخواست بعدی که با همان بایت‌ها شروع می‌شود دوباره از آن استفاده کند: خواندن از کش حدود یک‌دهم ورودی معمولی هزینه دارد (روی بعضی جدیدترین مدل‌ها حتی کمتر) و سریع‌تر برمی‌گردد. نوشتن در کش کمی گران‌تر است (۱٫۲۵ برابر برای کش پیش‌فرض ۵ دقیقه‌ای، ۲ برابر برای گزینهٔ یک‌ساعته).

Think of it like thisمثل این است که…

Caching is like a chef's mise en place: chop the onions once in the morning; every order that needs onions is faster all day.

کش مثل آماده‌سازی مواد آشپز (میزانپلاس) است: صبح یک بار پیازها را خرد کن؛ تمام روز هر سفارشی که پیاز لازم دارد سریع‌تر آماده می‌شود.

قانون‌های کش پرامپتRules of prompt caching

صفحهٔ رسمی ↗

The rules that decide whether you get a cache hit:

  • Exact prefix match. The cache key is the exact content up to the breakpoint. Change one character earlier in the prompt and everything after it misses.
  • Order: tools → system → messages. A breakpoint on the last system block caches tools and system together.
  • Up to 4 breakpoints per request; or use the top-level automatic cache_control to let the API place one for you.
  • Minimum length: prefixes shorter than a model-specific minimum (512 tokens on the newest models, up to 4,096 on some older ones) silently don't cache.
  • Lifetime: 5 minutes by default, refreshed on every hit; 1 hour if you ask ("ttl": "1h").

قانون‌هایی که تعیین می‌کنند از کش استفاده می‌شود یا نه:

  • تطابق دقیق پیشوند. کلید کش، محتوای دقیق تا نقطهٔ کش است. یک کاراکتر را جایی جلوتر در پرامپت عوض کن تا همه‌چیزِ بعد از آن از کش نخورد.
  • ترتیب: ابزارها ← سیستم ← پیام‌ها. نقطهٔ کش روی آخرین بلوک سیستم، ابزارها و سیستم را با هم کش می‌کند.
  • حداکثر ۴ نقطهٔ کش در هر درخواست؛ یا از cache_control خودکار در سطح بالا استفاده کن تا API خودش یکی بگذارد.
  • حداقل طول: پیشوندهای کوتاه‌تر از یک حداقلِ مخصوص هر مدل (۵۱۲ توکن روی جدیدترین مدل‌ها و تا ۴٬۰۹۶ روی بعضی مدل‌های قدیمی‌تر) بی‌صدا کش نمی‌شوند.
  • عمر: به‌طور پیش‌فرض ۵ دقیقه که با هر استفاده تازه می‌شود؛ اگر بخواهی ۱ ساعت ("ttl": "1h").

Watch outحواست باشد

Silent cache killers: a timestamp or random ID in the system prompt, tools listed in a different order, JSON with unsorted keys. They make every request a "new" prompt. Keep the stable part truly stable and put changing details after the breakpoint.

قاتل‌های بی‌صدای کش: یک برچسب زمان یا شناسهٔ تصادفی در پرامپت سیستمی، ابزارهایی که با ترتیب متفاوت فهرست شده‌اند، JSON با کلیدهای نامرتب. این‌ها هر درخواست را به یک پرامپت «تازه» تبدیل می‌کنند. بخش ثابت را واقعاً ثابت نگه دار و جزئیات متغیر را بعد از نقطهٔ کش بگذار.

Think of it like thisمثل این است که…

The cache is a coat check: you get your coat back only with the exact same ticket. A ticket with one digit changed gets you nothing.

کش مثل رخت‌کن است: فقط با همان بلیت دقیق کتت را پس می‌گیری. بلیتی که یک رقمش عوض شده هیچ چیزی به تو نمی‌دهد.

کش پرامپت در عملPrompt caching in action

صفحهٔ رسمی ↗

Measure, don't assume. The response's usage tells you exactly what happened: cache_creation_input_tokens (written to cache this time), cache_read_input_tokens (served from cache) and input_tokens (the uncached tail). Send the same long prefix twice: the first call writes, the second reads.

اندازه بگیر، فرض نکن. usage در پاسخ دقیقاً می‌گوید چه اتفاقی افتاده: cache_creation_input_tokens (این بار در کش نوشته شد)، cache_read_input_tokens (از کش خوانده شد) و input_tokens (دنبالهٔ کش‌نشده). یک پیشوند طولانی را دو بار بفرست: فراخوانی اول می‌نویسد، دومی می‌خواند.

Pro tipنکتهٔ طلایی

If cache_read_input_tokens stays at 0 on repeated calls, something in the prefix changes every time. Log two request bodies and diff them; the culprit is usually a date or an unordered dictionary.

اگر cache_read_input_tokens در فراخوانی‌های تکراری روی ۰ می‌ماند، چیزی در پیشوند هر بار عوض می‌شود. بدنهٔ دو درخواست را ثبت کن و با هم مقایسه کن؛ مقصر معمولاً یک تاریخ یا یک دیکشنری بی‌ترتیب است.

اجرای کد و Files APICode execution and the Files API

صفحهٔ رسمی ↗

Two features that work beautifully together:

  • The Files API uploads a file once (CSV, PDF, image) and gives you a file_id to reference in later requests, instead of re-sending the bytes.
  • Code execution is a server tool: Claude writes and runs Python in a sandboxed container (with pandas, matplotlib and friends, no internet). It can compute real numbers, make charts and produce files you download afterwards.

Together: "upload sales.csv, find trends, and make a chart", with numbers that are calculated, not guessed.

دو قابلیت که با هم عالی کار می‌کنند:

  • Files API یک فایل را یک بار بارگذاری می‌کند (CSV، PDF، تصویر) و یک file_id می‌دهد که در درخواست‌های بعدی به آن ارجاع بدهی، به جای این‌که بایت‌ها را دوباره بفرستی.
  • اجرای کد یک ابزار سمت سرور است: Claude در یک کانتینر ایزوله (با pandas، matplotlib و دوستانشان، بدون اینترنت) پایتون می‌نویسد و اجرا می‌کند. می‌تواند عددهای واقعی حساب کند، نمودار بکشد و فایل‌هایی بسازد که بعداً دانلودشان می‌کنی.

با هم: «sales.csv را بارگذاری کن، روندها را پیدا کن و نمودار بکش»، با عددهایی که محاسبه شده‌اند، نه حدس زده.

Files API روی Amazon Bedrock و Google Vertex AI در دسترس نیست. و هر اسم فایلی را که روی دیسک می‌نویسی پاک‌سازی کن (فقط اسم پایه را استفاده کن) تا یک فایل تولیدشده نتواند از پوشهٔ خروجی‌ات بیرون بزند.

۵۲

درس ۵۲ · Lesson 52

آشنایی با MCPIntroducing MCP

صفحهٔ رسمی ↗

In the tool-use section you wrote every tool yourself. Imagine integrating GitHub: dozens of tools (issues, pull requests, repos...), each needing a schema and a function. MCP (Model Context Protocol) moves that work into an MCP server that someone writes once and everyone reuses. Your app becomes an MCP client that asks the server "what tools do you have?" and calls them. MCP servers offer three things: tools, resources (read-only data) and prompts (ready-made instructions).

This section mirrors the separate course; for full step-by-step code, see Introduction to MCP in this handout.

در بخش استفاده از ابزار، همهٔ ابزارها را خودت نوشتی. حالا تصور کن می‌خواهی GitHub را وصل کنی: ده‌ها ابزار (issueها، pull requestها، مخزن‌ها...)، که هر کدام اسکیما و تابع لازم دارد. MCP (پروتکل زمینهٔ مدل) این کار را به یک سرور MCP منتقل می‌کند که یک نفر یک بار می‌نویسد و همه دوباره استفاده‌اش می‌کنند. اپ تو یک کلاینت MCP می‌شود که از سرور می‌پرسد «چه ابزارهایی داری؟» و صدایشان می‌زند. سرورهای MCP سه چیز ارائه می‌دهند: ابزارها، منابع (دادهٔ فقط‌خواندنی) و پرامپت‌ها (دستورهای آماده).

این بخش با دورهٔ جداگانه‌اش یکی است؛ برای کد کامل قدم به قدم، دورهٔ آشنایی با MCP در همین جزوه را ببین.

Think of it like thisمثل این است که…

MCP is the USB port for AI: instead of a custom cable for every device, one standard plug works with any device that supports it.

MCP درگاه USB هوش مصنوعی است: به جای یک کابل اختصاصی برای هر دستگاه، یک دوشاخهٔ استاندارد با هر دستگاهی که پشتیبانی‌اش کند کار می‌کند.

درس ۵۳ · Lesson 53

کلاینت‌های MCPMCP clients

صفحهٔ رسمی ↗

The client sits inside your app and talks to the server over a transport: standard input/output (stdio) for a server running on the same machine, or HTTP for remote servers. The flow for one question: your app asks the server for its tool list → sends the question + tools to Claude → Claude returns tool_use → the client asks the server to run that tool → the result goes back to Claude → final answer.

کلاینت داخل اپ تو می‌نشیند و از طریق یک ترابری (transport) با سرور حرف می‌زند: ورودی/خروجی استاندارد (stdio) برای سروری که روی همان دستگاه اجرا می‌شود، یا HTTP برای سرورهای دور. جریان یک سؤال: اپ از سرور فهرست ابزارهایش را می‌گیرد ← سؤال و ابزارها را برای Claude می‌فرستد ← Claude یک tool_use برمی‌گرداند ← کلاینت از سرور می‌خواهد آن ابزار را اجرا کند ← نتیجه به Claude برمی‌گردد ← جواب نهایی.

Pro tipنکتهٔ طلایی

Your app still runs the Claude side of the conversation. MCP only standardizes how tools are discovered and executed; the tool-use loop you learned stays the same.

سمت Claudeِ گفت‌وگو را هنوز اپ تو اجرا می‌کند. MCP فقط استاندارد می‌کند که ابزارها چطور کشف و اجرا شوند؛ حلقهٔ استفاده از ابزار که یاد گرفتی همان می‌ماند.

تعریف منابعDefining resources

صفحهٔ رسمی ↗

Resources are read-only data the server exposes, like GET endpoints in a web API. A direct resource has a fixed URI (docs://documents → the list of document ids); a templated resource has parameters in the URI (docs://documents/{doc_id} → one document). Resources are typically used by the app (e.g., to fill an autocomplete or attach a document to the prompt), while tools are chosen by Claude.

منابع داده‌های فقط‌خواندنی‌اند که سرور ارائه می‌دهد، مثل نقطه‌های GET در یک وب API. یک منبع مستقیم URI ثابت دارد (docs://documents ← فهرست شناسهٔ سندها)؛ یک منبع الگودار در URI پارامتر دارد (docs://documents/{doc_id} ← یک سند). منابع معمولاً به دست اپ استفاده می‌شوند (مثلاً برای پر کردن تکمیل خودکار یا پیوست کردن یک سند به پرامپت)، در حالی که ابزارها را Claude انتخاب می‌کند.

Think of it like thisمثل این است که…

Tools are buttons Claude can press; resources are files on a shelf your app can grab and hand over.

ابزارها دکمه‌هایی‌اند که Claude می‌تواند فشار دهد؛ منابع پرونده‌هایی روی قفسه‌اند که اپ تو می‌تواند بردارد و تحویل بدهد.

تعریف پرامپت‌هاDefining prompts

صفحهٔ رسمی ↗

Prompts are reusable, well-tested instruction templates that the server offers, so users don't have to write expert prompts themselves. درس ۶۲ · Lesson 62

مرور MCPMCP review

صفحهٔ رسمی ↗

Who controls what? This is the key summary of MCP:

  • Tools are model-controlled: Claude decides when to call them.
  • Resources are app-controlled: your code decides when to fetch and include them.
  • Prompts are user-controlled: the user picks them (often as slash commands).

When designing a server, ask "who should trigger this?" and you'll know which primitive to use.

چه کسی چه چیزی را کنترل می‌کند؟ این خلاصهٔ کلیدی MCP است:

  • ابزارها در کنترل مدل‌اند: Claude تصمیم می‌گیرد کی صدایشان بزند.
  • منابع در کنترل اپ‌اند: کد تو تصمیم می‌گیرد کی بگیردشان و اضافه‌شان کند.
  • پرامپت‌ها در کنترل کاربرند: کاربر انتخابشان می‌کند (اغلب به شکل فرمان اسلش).

موقع طراحی یک سرور بپرس «چه کسی باید این را راه بیندازد؟» تا بفهمی از کدام قطعه استفاده کنی.

Think of it like thisمثل این است که…

In a restaurant: the chef (Claude) decides which kitchen tools to use, the manager (your app) decides what's on the table, and the customer (user) picks from the menu.

در یک رستوران: سرآشپز (Claude) تصمیم می‌گیرد از کدام وسایل آشپزخانه استفاده کند، مدیر (اپ تو) تصمیم می‌گیرد چه چیزی روی میز باشد و مشتری (کاربر) از منو انتخاب می‌کند.

درس ۶۷ · Lesson 67

ایجنت‌ها و گردش‌کارهاAgents and workflows

صفحهٔ رسمی ↗

Two ways to build with LLMs:

  • Workflows: you know the steps in advance, so your code orchestrates a fixed sequence of Claude calls. Predictable and easy to test.
  • Agents: you give Claude tools and a goal, and Claude decides the steps in a loop. Flexible, for problems whose steps you can't predict.

The next lessons cover the classic workflow patterns, then what makes agents work.

دو راه برای ساختن با مدل‌های زبانی:

  • گردش‌کارها (workflows): قدم‌ها را از قبل می‌دانی؛ پس کد تو یک دنبالهٔ ثابت از فراخوانی‌های Claude را هماهنگ می‌کند. قابل‌پیش‌بینی و آسان برای آزمودن.
  • ایجنت‌ها (agents): به Claude ابزار و هدف می‌دهی و Claude تصمیم می‌گیرد قدم‌ها چه باشند، در یک حلقه. انعطاف‌پذیر، برای مسئله‌هایی که قدم‌هایشان را نمی‌توانی پیش‌بینی کنی.

درس‌های بعدی الگوهای کلاسیک گردش‌کار را پوشش می‌دهند و بعد این‌که چه چیزی ایجنت‌ها را کارآمد می‌کند.

Think of it like thisمثل این است که…

A workflow is a train on rails: fast and reliable, but only goes where the tracks go. An agent is a taxi driver: can go anywhere, but you trust their judgment on the route.

گردش‌کار مثل قطار روی ریل است: سریع و قابل‌اعتماد، ولی فقط جایی می‌رود که ریل هست. ایجنت مثل راننده تاکسی است: هر جایی می‌تواند برود، ولی باید به قضاوتش دربارهٔ مسیر اعتماد کنی.

Key wordsواژه‌های کلیدی

Workflowگردش‌کار
دنباله‌ای از فراخوانی‌های مدل که کد تو از قبل مسیرش را تعیین کرده.
Agentایجنت (عامل)
سیستمی که در آن مدل با ابزارها و در یک حلقه، خودش قدم‌های رسیدن به هدف را انتخاب می‌کند.

درس ۶۸ · Lesson 68

گردش‌کارهای موازیParallelization workflows

صفحهٔ رسمی ↗

Split a task into independent subtasks, run them at the same time (separate Claude calls), then aggregate the results in a final call. Each call gets a small, focused prompt, which is usually more accurate than one giant prompt doing everything.

یک کار را به زیرکارهای مستقل تقسیم کن، همزمان اجرایشان کن (فراخوانی‌های جدای Claude) و بعد نتیجه‌ها را در یک فراخوانی نهایی جمع‌بندی کن. هر فراخوانی یک پرامپت کوچک و متمرکز می‌گیرد که معمولاً از یک پرامپت غول‌پیکر که همه‌کار می‌کند دقیق‌تر است.

Real exampleمثال واقعی

Choosing a material for a bike frame: four parallel calls each evaluate one option (aluminum, steel, carbon fiber, titanium) against weight, cost and durability; a fifth call compares the four reports and recommends one.

انتخاب جنس برای بدنهٔ دوچرخه: چهار فراخوانی موازی، هر کدام یک گزینه را (آلومینیوم، فولاد، فیبر کربن، تیتانیوم) از نظر وزن، هزینه و دوام ارزیابی می‌کنند؛ فراخوانی پنجم چهار گزارش را مقایسه می‌کند و یکی را پیشنهاد می‌دهد.

Think of it like thisمثل این است که…

It's a group project done right: everyone researches one country at the same time, then one person writes the summary.

مثل یک کار گروهی درست و حسابی است: همه همزمان دربارهٔ یک کشور تحقیق می‌کنند، بعد یک نفر جمع‌بندی را می‌نویسد.

۶۹

درس ۶۹ · Lesson 69

گردش‌کارهای زنجیره‌ایChaining workflows

صفحهٔ رسمی ↗

Chaining breaks a big task into sequential steps, each a separate call whose output feeds the next. It shines when one prompt has too many requirements and Claude keeps missing some: do the main job first, then fix specific issues in focused follow-up calls. You can also put code checks between steps (e.g., "is the output under 280 characters?").

زنجیره کردن یک کار بزرگ را به قدم‌های پشت سر هم تقسیم می‌کند؛ هر قدم یک فراخوانی جداست که خروجی‌اش ورودی قدم بعد می‌شود. وقتی می‌درخشد که یک پرامپت نیازمندی‌های خیلی زیادی دارد و Claude مدام چندتایشان را جا می‌اندازد: اول کار اصلی را انجام بده، بعد مشکل‌های مشخص را در فراخوانی‌های پیگیریِ متمرکز درست کن. می‌توانی بین قدم‌ها چک‌های کدی هم بگذاری (مثلاً «خروجی زیر ۲۸۰ کاراکتر است؟»).

Real exampleمثال واقعی

  1. Research a topic → 2) write an article from the research → 3) separate call: "Rewrite this article: remove any mention of being an AI, avoid emojis, and replace jargon with plain words." Step 3 succeeds far more often than putting all those rules into step 2.
  1. دربارهٔ یک موضوع تحقیق کن ← ۲) از روی تحقیق یک مقاله بنویس ← ۳) فراخوانی جدا: «این مقاله را بازنویسی کن: هر اشاره‌ای به هوش مصنوعی بودن را حذف کن، از ایموجی استفاده نکن و اصطلاحات فنی را با کلمه‌های ساده عوض کن.» قدم ۳ خیلی بیشتر از وقتی که همهٔ آن قانون‌ها را در قدم ۲ بگذاری موفق می‌شود.

Think of it like thisمثل این است که…

Chaining is an assembly line: one station welds, the next paints, the next inspects. No single worker has to remember everything.

زنجیره کردن مثل خط مونتاژ است: یک ایستگاه جوش می‌دهد، بعدی رنگ می‌زند، بعدی بازرسی می‌کند. هیچ کارگری مجبور نیست همه‌چیز را یادش بماند.

۷۰

درس ۷۰ · Lesson 70

گردش‌کارهای مسیریابیRouting workflows

صفحهٔ رسمی ↗

Routing first classifies the input, then sends it to a specialized prompt or pipeline for that category. Example: a video-script app classifies a topic as *educational*, *entertainment* or *product review*, and each category has its own expert prompt with the right tone and structure. Use a fast model for the classification step.

مسیریابی اول ورودی را دسته‌بندی می‌کند، بعد آن را به یک پرامپت یا خط لولهٔ تخصصی برای همان دسته می‌فرستد. مثال: یک اپ فیلم‌نامهٔ ویدئو موضوع را *آموزشی*، *سرگرمی* یا *نقد محصول* دسته‌بندی می‌کند و هر دسته پرامپت متخصص خودش را با لحن و ساختار مناسب دارد. برای قدم دسته‌بندی از یک مدل سریع استفاده کن.

Think of it like thisمثل این است که…

Routing is the hospital triage desk: a quick check decides whether you go to cardiology, orthopedics or the pharmacy.

مسیریابی مثل میز تریاژ بیمارستان است: یک بررسی سریع تصمیم می‌گیرد به بخش قلب بروی، ارتوپدی یا داروخانه.

درس ۷۱ · Lesson 71

ایجنت‌ها و ابزارهاAgents and tools

صفحهٔ رسمی ↗

Agents are only as capable as their tools. The lesson's key insight: give agents abstract, general-purpose tools (read a file, write a file, run a command, search) rather than dozens of hyper-specific ones. Claude can combine simple tools in creative ways to solve problems you never planned for, which is exactly how Claude Code works with a handful of tools.

ایجنت‌ها فقط به اندازهٔ ابزارهایشان توانا هستند. بینش کلیدی این درس: به ایجنت‌ها ابزارهای انتزاعی و همه‌منظوره بده (خواندن فایل، نوشتن فایل، اجرای فرمان، جست‌وجو)، نه ده‌ها ابزار بیش از حد خاص. Claude می‌تواند ابزارهای ساده را به شکل‌های خلاقانه ترکیب کند تا مسئله‌هایی را حل کند که هیچ‌وقت برایشان برنامه نریخته بودی؛ دقیقاً همان‌طور که Claude Code با چند ابزار انگشت‌شمار کار می‌کند.

Real exampleمثال واقعی

Instead of a create_weekly_sales_chart tool, give run_python and read_file. Now the same agent can make weekly charts, monthly charts, or a chart nobody thought of.

به جای ابزار create_weekly_sales_chart، ابزارهای run_python و read_file را بده. حالا همان ایجنت می‌تواند نمودار هفتگی بسازد، نمودار ماهانه، یا نموداری که به فکر هیچ‌کس نرسیده بود.

Think of it like thisمثل این است که…

LEGO bricks vs a finished toy: the toy does one thing; the bricks build anything.

آجرهای لگو در برابر یک اسباب‌بازی آماده: اسباب‌بازی یک کار می‌کند؛ آجرها هر چیزی می‌سازند.

درس ۷۲ · Lesson 72

وارسی محیطEnvironment inspection

صفحهٔ رسمی ↗

An agent must see the results of its actions, or it's working blindfolded. Computer use returns a screenshot after every action so Claude knows what happened. Coding agents read a file before editing it and run tests after. When you design an agent, ask: after each action, how does the agent find out whether it worked?

یک ایجنت باید نتیجهٔ کارهایش را ببیند، وگرنه با چشم‌بند کار می‌کند. استفاده از کامپیوتر بعد از هر کار یک اسکرین‌شات برمی‌گرداند تا Claude بفهمد چه اتفاقی افتاد. ایجنت‌های برنامه‌نویسی قبل از ویرایش، فایل را می‌خوانند و بعدش تست اجرا می‌کنند. وقتی ایجنتی طراحی می‌کنی بپرس: بعد از هر کار، ایجنت چطور می‌فهمد جواب داده یا نه؟

Real exampleمثال واقعی

A video-editing agent cuts a clip, then extracts frames at the cut points and checks them, and runs a speech-to-text pass to confirm no sentence was cut in half.

یک ایجنت تدوین ویدئو یک کلیپ را می‌برد، بعد سر نقطه‌های برش چند فریم بیرون می‌کشد و چکشان می‌کند و یک دور تبدیل گفتار به متن اجرا می‌کند تا مطمئن شود هیچ جمله‌ای نصفه بریده نشده.

Think of it like thisمثل این است که…

Like painting a wall in a dark room vs with the lights on: same brush, very different result.

مثل رنگ زدن دیوار در اتاق تاریک در برابر اتاق روشن: همان قلم‌مو، نتیجه‌ای کاملاً متفاوت.

درس ۷۳ · Lesson 73

گردش‌کار در برابر ایجنتWorkflows vs agents

صفحهٔ رسمی ↗

The course's advice: prefer workflows when you can, use agents when you must. Workflows are easier to test, cheaper, more predictable and complete tasks more reliably. Agents are more flexible and handle open-ended problems, but they're harder to evaluate and can wander. Users want products that work, not the most "agentic" design.

توصیهٔ دوره: هر جا می‌توانی گردش‌کار، هر جا مجبوری ایجنت. گردش‌کارها آسان‌تر آزموده می‌شوند، ارزان‌ترند، قابل‌پیش‌بینی‌ترند و کارها را مطمئن‌تر تمام می‌کنند. ایجنت‌ها انعطاف‌پذیرترند و مسئله‌های باز را حل می‌کنند، ولی ارزیابی‌شان سخت‌تر است و ممکن است سرگردان شوند. کاربرها محصولی می‌خواهند که کار کند، نه «ایجنتی‌ترین» طراحی را.

Pro tipنکتهٔ طلایی

Cool tip: if you need a hosted agent (long-running, with a sandbox, files and tools) without writing the loop yourself, look at Claude Managed Agents (beta), covered in Claude Platform 101 in this handout.

نکتهٔ خفن: اگر یک ایجنت میزبانی‌شده لازم داری (طولانی‌مدت، با محیط ایزوله، فایل و ابزار) بدون این‌که حلقه را خودت بنویسی، سراغ Claude Managed Agents (بتا) برو که در Claude Platform 101 همین جزوه آمده.

Think of it like thisمثل این است که…

Don't hire a detective to deliver a pizza. Use a delivery route (workflow) for known jobs, and the detective (agent) for mysteries.

برای رساندن پیتزا کارآگاه استخدام نکن. برای کارهای شناخته‌شده از مسیر پیک (گردش‌کار) استفاده کن و برای معماها از کارآگاه (ایجنت).

  • کش: اول پیشوند ثابت، نقطهٔ کش بعد از آن، cache_read_input_tokens را چک کن.
  • MCP: ابزارها در کنترل مدل، منابع در کنترل اپ، پرامپت‌ها در کنترل کاربر.
